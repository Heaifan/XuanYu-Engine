# 玄域引擎 AI 开发宪法

以下规则为后续玄域引擎开发、审计、修复、规划和 Codex 协作的统一执行标准。参与项目的 AI 必须严格遵守，不得擅自弱化、规避或选择性执行。

---

## 一、总执行原则

默认执行流程：

```text
读取最少必要信息
→ 判断问题
→ 直接实施最小可行修改
→ 完成验证
→ 提交本地 Commit
→ Push 到 GitHub 远端当前工作分支
→ 输出完整报告
```

普通、低风险、可验证、可回退的修改，AI 应主动完成，不得频繁停下来请示。

只有遇到以下情况才暂停：

- 产品方向或需求存在明显冲突；
- 工作区出现来源不明的修改；
- 修改将明显扩大任务范围；
- 涉及重大架构、兼容性、依赖、权限或 Git 历史操作；
- 需要删除、迁移、重命名已有内容；
- 现有证据不足，继续修改可能造成破坏。

核心原则：

> 能局部完成、可验证、可回退、不改变重大方向，就直接做。  
> 不得让提问和流程阻断正常开发进度。

---

## 二、绝对红线

以下规则任何情况下都不能绕过。

### 1. 5+100 代码规则

- 每个手写 `.cs`、`.axaml`、`.js` 文件不得超过 100 行；
- 100 行是硬红线，无例外；
- 文件少于 100 行仍必须保持单一职责；
- 禁止通过压缩格式、合并语句、删除必要注释来降低行数；
- 禁止通过大量无意义转发类进行假拆分；
- 拆分后调用链不得比原来更难理解；
- 每个文件必须有明确职责、状态所有权和生命周期。

本轮触碰到超长文件时，必须同步治理，但不得借机重构整个模块。

### 2. 分层边界

- `Editor.UI` 不得直接依赖 Vulkan 实现；
- `Render.Abstractions` 不得引用 `Silk.NET.Vulkan`；
- UI、抽象层、实现层、平台组合根之间必须保持明确依赖方向；
- 不得为图方便破坏既定架构边界。

### 3. 敏感信息禁止入库

禁止提交：

- API Key；
- Token；
- 密码；
- 私钥；
- Cookie；
- 含凭据的连接字符串；
- 用户姓名、邮箱等不必要个人信息；
- 精确本机绝对路径；
- 本机账号信息。

必须使用：

- 相对路径；
- 环境变量；
- 本地忽略配置；
- 示例占位符。

发现仓库已有敏感信息时：

- 立即停止扩散；
- 明确报告；
- 不得擅自改写 Git 历史。

### 4. AI 聊天记录禁止提交

以下内容一律不得提交到仓库：

- 用户与 AI 的聊天记录；
- 对话导出；
- 提示词草稿；
- AI 执行记录；
- 临时审计对话；
- AI 思考过程；
- 临时生成的任务聊天日志。

不得把这些内容包装成“开发文档”后提交。

发现此类文件进入工作区时，必须先报告。

### 5. 禁止掩盖失败

禁止：

- 空 `catch`；
- 吞掉异常；
- 记录日志后继续使用不可信状态；
- 削弱测试断言；
- 扩大容差只为测试变绿；
- 删除失败测试；
- 禁用、跳过测试而不请示；
- 用 TODO 掩盖未完成；
- 用日志或占位代码伪装功能完成；
- 关闭分析器或降低规则等级换取通过；
- 用 `.gitignore` 掩盖异常文件。

## 三、AI 的自主权限

以下事项原则上允许 AI 当轮直接处理，完成后汇报。

### 1. 普通 Bug 修复

- 可直接定位并修复；
- 必须保持未涉及行为兼容；
- 修复后增加相关回归验证；
- 不得顺手重构无关代码。

### 2. UI 调整

允许先修改、后验收：

- 布局；
- 控件位置；
- 尺寸；
- 间距；
- 局部视觉样式；
- 为当前功能新增必要控件。

要求：

- 遵循现有视觉语言；
- 不得使用字符、Unicode、Emoji 作为图标；
- 图标必须使用 SVG 或 PathIcon；
- 必须说明可见变化和回退方式；
- 用户不满意时，下一轮直接回退或重做。

### 3. 新增必要小文件

任务确有需要时，可新增小型单一职责文件，但必须说明：

- 文件职责；
- 新增原因；
- 为什么现有文件不适合承载；
- 是否影响公共接口；
- 是否更新 `file-tree.md`；
- 是否更新 `changelog.md`。

新增重大模块、基础设施、目录层级、公共抽象或持久化体系仍需事前请示。

### 4. 局部性能优化

允许直接处理：

- 高频重复分配；
- 重复刷新；
- 日志洪泛；
- 无意义 Present；
- 明确可证实的局部性能问题。

要求：

- 必须有前后依据；
- 不得只写“理论上更快”；
- 不得牺牲正确性、可读性和调试能力。

线程模型、缓存体系、渲染管线、批处理架构等系统级优化必须先提案。

### 5. 局部线程安全修复

可直接处理：

- UI 线程派发；
- 取消令牌；
- 局部锁范围；
- 明确竞态；
- 生命周期停止和释放问题。

禁止：

- 用 `Task.Run` 掩盖卡顿；
- 随意增加锁碰运气；
- 在不明确状态所有权时修改线程逻辑。

新增长期后台线程、渲染线程、调度器或改变线程模型必须事前请示。

## 四、计划与范围控制

### 1. 计划深度按任务复杂度决定

#### 极小任务

只需说明：

- 问题；
- 修改点；
- 验证方式。

#### 普通任务

需说明：

- 目标；
- 修改范围；
- 涉及文件；
- 验证方式；
- 风险。

#### 复杂任务

需说明：

- 当前情况；
- 影响；
- 根因判断；
- 修改阶段；
- 风险；
- 回滚方式；
- 验收条件。

不得为了“规划完整”拖延实际开发。

### 2. 范围控制

- 计划内文件可直接修改；
- 必要关联文件可补充，但必须在报告中说明；
- 不得顺便清理无关代码；
- 不得借当前任务重构整个模块；
- 涉及公共接口、持久化、多模块或重大架构扩围时必须暂停。

---

## 五、Bug 排查规范

复杂、反复、根因不明确的 Bug，必须采用：

```text
列出可能涉及的文件
→ 增加中文探针日志
→ 运行一次
→ 根据日志定位
→ 再实施修复
```

不得直接猜根因或盲改。

探针规则：

- 使用中文前缀；
- 字段和结果使用中文；
- 高频事件不得进入普通日志；
- 临时探针与正式日志必须区分；
- 临时探针修复后不能擅自删除；
- 需列出待删除项，经确认后下一轮删除；
- 有长期价值的探针可以转为正式诊断功能。

---

## 六、日志规范

### 高频链路

以下高频事件不得进入普通日志：

- PointerMoved；
- Hover；
- DragPreview；
- RenderFrame；
- 高频 Resize；
- 高频状态刷新。

### Preview / Commit 原则

- Preview：只更新场景预览和渲染；
- Commit / Cancel：才更新 WorldState、Inspector、Diagnostics 等重负载状态。

禁止高频交互直接刷新重型 UI 或诊断系统。

---

## 七、测试与验证规范

### 1. 测试修改原则

- 实现不符合需求：修实现；
- 需求或公共契约明确变化：可同步修改测试；
- 测试本身错误：必须提供证据；
- 禁止迁就测试；
- 禁止弱化断言；
- 禁止删除失败用例；
- 删除、跳过、禁用测试必须事前请示。

最终报告必须分别列出：

- 实现变化；
- 测试变化。

### 2. 分层验证要求

#### 文档任务

验证：

- 格式；
- 链接；
- 内容一致性；
- 文件引用；
- 事实准确性。

#### 普通代码任务

验证：

- Restore；
- Build；
- 相关测试；
- 警告数量。

#### UI / 输入任务

验证：

- Build；
- 启动；
- 真实交互；
- 未受影响功能回归。

#### Vulkan / 生命周期任务

验证：

- Build；
- 真机运行；
- Resize；
- Present；
- 窗口关闭；
- 资源释放顺序；
- 重建与恢复。

#### 存档 / 场景任务

必须验证：

```text
保存
→ 关闭
→ 重开
→ 数据一致
```

#### 性能任务

必须说明：

- 测量场景；
- 修改前结果；
- 修改后结果；
- 未覆盖范围。

### 3. 失败处理

Build 或测试失败时：

- 必须依据真实错误和日志修复；
- 最多连续尝试两轮；
- 两轮后仍失败，或修复需要明显扩围时，立即停止；
- 报告事实、疑点、当前工作区状态和下一步建议；
- 不得无限循环试错。

---

## 八、异常处理规范

允许调整异常策略，但必须满足：

- 禁止空 `catch`；
- 可恢复异常必须记录中文上下文；
- 可恢复异常必须进入明确降级路径；
- 不可恢复异常必须快速失败；
- 失败时必须正确释放资源；
- 生命周期、渲染、存档、数据一致性异常不得静默吞掉；
- 禁止异常后继续使用不可信状态。

最终报告必须说明：

- 触发条件；
- 处理方式；
- 失败后状态；
- 是否降级；
- 是否影响其他模块。

改变跨模块异常语义必须事前请示。

---

## 九、存档与数据兼容

- 所有持久化数据必须有 Schema 版本；
- 新增可选字段且有安全默认值，可直接处理；
- 删除字段、改字段含义、类型、单位、坐标系、序列化格式，必须事前请示；
- 必须说明旧数据如何读取；
- 必须说明迁移失败如何处理；
- 必须提供回滚思路；
- 禁止旧数据读取失败后静默重置；
- 禁止未经确认覆盖或丢弃旧数据。

---

## 十、依赖与配置规范

### 1. 第三方依赖

新增或升级第三方依赖必须先提案，内容至少包括：

- 名称；
- 版本；
- 用途；
- 为什么现有方案不够；
- 无依赖替代方案；
- 许可证；
- 维护情况；
- 体积；
- 运行时影响；
- 兼容性；
- 移除与回滚方式。

未经明确批准不得引入。

### 2. 配置与项目文件

低风险、局部、可回退的配置修改可直接完成，但必须说明：

- 修改前后；
- 修改原因；
- 影响范围；
- 验证方式；
- 回滚方式；
- 是否新增依赖。

以下事项必须事前请示：

- 目标框架；
- 发布设置；
- 安全权限；
- 全局编译规则；
- 解决方案结构；
- 多项目构建链；
- 新增系统权限。

---

## 十一、生成文件和非源码资产

不得提交：

- `bin/`；
- `obj/`；
- 缓存；
- 临时日志；
- 测试输出；
- 崩溃转储；
- 可稳定重建的构建产物。

可提交：

- 正式资源；
- 必须分发的 Shader 产物；
- Schema；
- 模板；
- 用户明确要求保留的生成结果。

新增大型二进制、模型、纹理、压缩包或第三方运行库时，必须先说明：

- 体积；
- 来源；
- 许可；
- 更新方式；
- 是否可替代。

---

## 十二、Git 规范

### 1. Commit

- 每个 Commit 应是独立可验证步骤；
- 真机修复应新增 Commit；
- 不得为了保持历史“漂亮”而覆盖已测试提交；
- 硬件验收失败后继续新增修复 Commit；
- 禁止默认修改已推送历史。

### 2. Push

自动验证通过并完成本地 Commit 后，必须 Push 到 GitHub 远端当前工作分支，作为多电脑开发的远端备份基线。

Push 规则：

- 默认 Push 当前工作分支到其跟踪远端分支；
- 不得因“未进入 main”而跳过 Push；
- Push 前必须确认 worktree、staged、untracked 状态；
- Push 后必须在最终报告中写明远端分支、Push 结果和 HEAD Hash；
- Push 只代表备份和同步，不代表正式封版。

以下操作仍然必须经用户明确确认：

- 合并到 `main`；
- 创建 Pull Request；
- 创建或移动 Tag；
- 创建 GitHub Release；
- 强推、Rebase、重写历史。

### 3. 分支

允许：

- 读取当前分支；
- 查看状态；
- 查看远程差异；
- 明确任务要求时创建和切换新分支。

禁止擅自执行：

- 合并；
- Rebase；
- 删除分支；
- 强推；
- 重写历史。

存在来源不明的未提交改动时，不得强行切换分支。

出现冲突时：

- 先报告冲突文件；
- 说明冲突原因；
- 不得擅自选择一方覆盖。

### 4. Tag 与 Release

- 开发过程中可更新版本号；
- 若应用存在可见主窗口标题，标题必须在产品名后显示当前开发版本号；
- 每轮版本推进时，窗口标题版本号必须与本轮 `changelog.md` 顶部版本保持一致；
- 本地 Commit 可使用对应版本；
- 正式 Tag、GitHub Release 和封版标记，必须验收通过并经用户确认；
- 不得提前打 Tag 等待测试；
- 已推送 Tag 不得擅自移动、覆盖或删除；
- Tag 出错时必须先报告。

---

## 十三、删除、移动与重命名

### 删除文件

必须：

- 列出完整文件；
- 说明删除原因；
- 分析依赖；
- 说明影响；
- 获得明确批准；
- 下一轮再执行。

不得同轮提议并删除。

### 移动或重命名

按删除级别处理，必须说明：

- 原路径；
- 新路径；
- 原因；
- 引用变化；
- Namespace；
- 依赖变化；
- 文档影响；
- 回滚方式。

即使只是修复拼写错误，也必须遵守。

---

## 十四、注释、文档和 TODO

### 注释与文档

- 与代码直接相关的注释必须同步更新；
- 过期、错误、误导性注释可以修正；
- 不得擅自删除事故原因、边界说明和历史妥协；
- 长期架构原则和开发规范不得改写原意；
- 注释应解释“为什么”，不得逐行复述代码；
- 文档与代码冲突时，必须指出并修正。

### TODO

允许存在，但必须说明：

- 原因；
- 触发条件；
- 责任范围。

禁止：

- “以后优化”；
- “待处理”；
- 用 TODO 掩盖未完成；
- 临时占位进入正式主流程。

所有新增 TODO 必须：

- 写入最终报告；
- 写入 `changelog.md`；
- 收口时列出仍存在的 TODO。

---

## 十五、警告与静态检查

- 本轮不得新增编译警告；
- 不得新增分析器告警；
- 不得新增静态检查问题；
- 本轮触碰文件中的既有警告原则上必须修复；
- 若修复会明显扩围，可保留，但必须说明原因、风险和处理条件；
- 禁止关闭分析器；
- 禁止降低规则等级；
- 禁止批量 `Suppress`；
- 单点抑制必须说明为什么该告警不适用。

---

## 十六、版本规范

### 开发期

格式：

```text
v0.<里程碑>.<模块>.<修订次数>-<类型>
```

示例：

```text
v0.1.6.1-fix
```

规则：

- 进入新里程碑，模块号从 `1` 开始；
- 进入新模块，修订次数从 `1` 开始；
- `RZ`、`VK`、`FIX` 等只作为末尾类型标签。

### 上线后

格式：

```text
v<上线年数>.<重大更新次数>.<小修订次数>
```

示例：

```text
v2.1.5
```

## 十七、文档同步规范

### `changelog.md`

任何开发修改都必须更新。

内容至少包括：

- 版本；
- 日期：必须记录本轮提交发生时的本地时间，精确到秒，格式为 `YYYY-MM-DD HH:mm:ss`；不得只写日期、不得只精确到分钟；
- 本轮目标；
- 主要变化；
- 修改范围；
- 验证结果；
- Commit Hash；
- 遗留问题。

### `file-tree.md`

以下情况必须更新：

- 新增文件；
- 删除文件；
- 移动文件；
- 重命名文件；
- 文件职责发生变化；
- 依赖边界发生变化。

每个文件说明至少包括：

- 路径；
- 单一职责；
- 不负责什么；
- 依赖边界。

## 十八、任务收口报告

每次开发修改，无论大小，必须输出以下五项。

### 1. Git 状态

- Push 状态；
- Tag 状态；
- Release 状态；
- 版本号；
- Commit Hash；

### 2. 文档状态

- `file-tree.md` 是否更新；
- `changelog.md` 是否更新；
- 未更新的原因。

### 3. 修改范围

列出：

- 实际修改文件；
- 每个文件 `+x / -y`；
- 修改摘要；
- Worktree 状态；
- Staged 状态；
- Untracked 状态；
- 计划范围与实际范围是否一致。

### 4. 可视化与人工验收

必须提供：

- 一份窗口内可视化 SVG；
- SVG 内标题、节点、说明和标注应尽量使用中文；仅代码标识、项目名、文件名、协议名等确需精确引用时保留英文；

### 5. 最终结论

- 当前是否通过；
- 是否可封版；
- 剩余问题；
- 未完成 TODO；
- 风险；
- 下一步建议。

不得虚构 Commit、Hash、Push、Tag、测试结果或真机状态。

## 二十、最终执行口径

AI 必须遵循以下判断顺序：

```text
是否违反绝对红线？
├─ 是 → 禁止执行
└─ 否
   ↓
是否属于重大决策？
├─ 是 → 提案并请示
└─ 否
   ↓
是否局部、可验证、可回退？
├─ 是 → 直接完成
└─ 否 → 缩小方案或报告风险
```

最终原则：

> 严格守住边界，但不得失去主动性。  
> 普通问题直接解决，重大问题才请示。  
> 不盲改、不造假、不掩盖、不扩围。  
> 所有结果必须可验证、可回退、可审计。
