# 玄域引擎 AI 开发宪法

以下规则为后续玄域引擎开发、审计、修复、规划和 Codex 协作的统一执行标准。参与项目的 AI 必须严格遵守，不得擅自弱化、规避或选择性执行。

---

## 一、总执行原则

默认执行流程：

```text
读取最少必要信息
→ 判断问题
→ 直接实施最小可行修改
→ 完成验证
→ 提交本地 Commit
→ Push 到 GitHub 远端当前工作分支
→ 输出完整报告
```

普通、低风险、可验证、可回退的修改，AI 应主动完成，不得频繁停下来请示。

只有遇到以下情况才暂停：

- 产品方向或需求存在明显冲突；
- 工作区出现来源不明的修改；
- 修改将明显扩大任务范围；
- 涉及重大架构、兼容性、依赖、权限或 Git 历史操作；
- 需要删除、迁移、重命名已有内容；
- 现有证据不足，继续修改可能造成破坏。

核心原则：

> 能局部完成、可验证、可回退、不改变重大方向，就直接做。  
> 不得让提问和流程阻断正常开发进度。

### 1. 宪法优先级

- 本开发宪法是项目协作的最高基础执行准则；
- 用户临时提示、审计建议或 AI 自行判断与本宪法冲突时，必须以本宪法为准；
- 禁止用“用户刚才说了”作为跳过 `changelog.md`、`file-tree.md`、验证、Commit、Push、5+100 或分层边界的理由；
- 如用户要求与宪法冲突，AI 必须说明冲突点、引用对应宪法要求，并执行符合宪法的最小方案；
- 最终报告必须明确写出被拒绝或修正的指令为什么不能照做，避免把违宪行为包装成“遵从用户要求”。

## 二、绝对红线

以下规则任何情况下都不能绕过。

### 1. 5+100 代码规则

- 每个手写 `.cs`、`.axaml`、`.js` 文件不得超过 100 行；
- 100 行是硬红线，无例外；
- 文件少于 100 行仍必须保持单一职责；
- 禁止通过压缩格式、合并语句、删除必要注释来降低行数；
- 禁止通过大量无意义转发类进行假拆分；
- 拆分后调用链不得比原来更难理解；
- 每个文件必须有明确职责、状态所有权和生命周期。

本轮触碰到超长文件时，必须同步治理，但不得借机重构整个模块。

### 2. 分层边界

- `Editor.UI` 不得直接依赖 Vulkan 实现；
- `Render.Abstractions` 不得引用 `Silk.NET.Vulkan`；
- UI、抽象层、实现层、平台组合根之间必须保持明确依赖方向；
- 不得为图方便破坏既定架构边界。

### 3. 敏感信息禁止入库

禁止提交：

- API Key；
- Token；
- 密码；
- 私钥；
- Cookie；
- 含凭据的连接字符串；
- 用户姓名、邮箱等不必要个人信息；
- 精确本机绝对路径；
- 本机账号信息。

必须使用：

- 相对路径；
- 环境变量；
- 本地忽略配置；
- 示例占位符。

发现仓库已有敏感信息时：

- 立即停止扩散；
- 明确报告；
- 不得擅自改写 Git 历史。

### 4. AI 聊天记录禁止提交

以下内容一律不得提交到仓库：

- 用户与 AI 的聊天记录；
- 对话导出；
- 提示词草稿；
- AI 执行记录；
- 临时审计对话；
- AI 思考过程；
- 临时生成的任务聊天日志。

不得把这些内容包装成“开发文档”后提交。

发现此类文件进入工作区时，必须先报告。

### 5. 禁止掩盖失败

禁止：

- 空 `catch`；
- 吞掉异常；
- 记录日志后继续使用不可信状态；
- 削弱测试断言；
- 扩大容差只为测试变绿；
- 删除失败测试；
- 禁用、跳过测试而不请示；
- 用 TODO 掩盖未完成；
- 用日志或占位代码伪装功能完成；
- 关闭分析器或降低规则等级换取通过；
- 用 `.gitignore` 掩盖异常文件。

## 三、AI 的自主权限

以下事项原则上允许 AI 当轮直接处理，完成后汇报。

### 1. 普通 Bug 修复

- 可直接定位并修复；
- 必须保持未涉及行为兼容；
- 修复后增加相关回归验证；
- 不得顺手重构无关代码。

### 2. UI 调整

允许先修改、后验收：

- 布局；
- 控件位置；
- 尺寸；
- 间距；
- 局部视觉样式；
- 为当前功能新增必要控件。

要求：

- 遵循现有视觉语言；
- 不得使用字符、Unicode、Emoji 作为图标；
- 图标必须使用 SVG 或 PathIcon；
- 必须说明可见变化和回退方式；
- 用户不满意时，下一轮直接回退或重做。

### 3. 新增必要小文件

任务确有需要时，可新增小型单一职责文件，但必须说明：

- 文件职责；
- 新增原因；
- 为什么现有文件不适合承载；
- 是否影响公共接口；
- 是否更新 `file-tree.md`；
- 是否更新 `changelog.md`。

新增重大模块、基础设施、目录层级、公共抽象或持久化体系仍需事前请示。

### 4. 局部性能优化

允许直接处理：

- 高频重复分配；
- 重复刷新；
- 日志洪泛；
- 无意义 Present；
- 明确可证实的局部性能问题。

要求：

- 必须有前后依据；
- 不得只写“理论上更快”；
- 不得牺牲正确性、可读性和调试能力。

线程模型、缓存体系、渲染管线、批处理架构等系统级优化必须先提案。

### 5. 局部线程安全修复

可直接处理：

- UI 线程派发；
- 取消令牌；
- 局部锁范围；
- 明确竞态；
- 生命周期停止和释放问题。

禁止：

- 用 `Task.Run` 掩盖卡顿；
- 随意增加锁碰运气；
- 在不明确状态所有权时修改线程逻辑。

新增长期后台线程、渲染线程、调度器或改变线程模型必须事前请示。

## 四、计划与范围控制

### 1. 计划深度按任务复杂度决定

#### 极小任务

只需说明：

- 问题；
- 修改点；
- 验证方式。

#### 普通任务

需说明：

- 目标；
- 修改范围；
- 涉及文件；
- 验证方式；
- 风险。

#### 复杂任务

需说明：

- 当前情况；
- 影响；
- 根因判断；
- 修改阶段；
- 风险；
- 回滚方式；
- 验收条件。

不得为了“规划完整”拖延实际开发。

### 2. 范围控制

- 计划内文件可直接修改；
- 必要关联文件可补充，但必须在报告中说明；
- 不得顺便清理无关代码；
- 不得借当前任务重构整个模块；
- 涉及公共接口、持久化、多模块或重大架构扩围时必须暂停。

### 3. 地基型架构原则

- 架构立足终局，能力逐步实现；允许少做功能，不允许把明显低扩展性的临时路径写成正式主架构。
- 对状态所有权、生命周期、空间查询、渲染数据流、资源体系、Undo、存档等地基型决策，不得以“当前规模小”“以后优化”为理由降低主路径标准。
- 规划必须区分“最小正确实现”和“最小能跑实现”：可以缩功能，不能降地基标准。
- 重要架构规划必须回答最终规模、规模增长复杂度、未来替换成本、临时设计扩散风险和本轮最小正确实现。
- 重要阶段必须定义 Entry Gate / Exit Gate；入口条件不满足时，不得把临时破解写入主链。
- 受控架构债务必须写清当前限制、暂留原因、允许存在范围、禁止扩散范围、必须解决阶段和未解决会阻断的后续能力，不得只写“以后优化”。
- 用户明确确认新的长期治理规则、架构原则或红线后，AI 必须在同一开发轮同步更新开发宪法和相关执行规则；未经用户确认的推测性规则不得擅自写入宪法。

## 五、Bug 排查规范

复杂、反复、根因不明确的 Bug，必须采用：

```text
列出可能涉及的文件
→ 增加中文探针日志
→ 运行一次
→ 根据日志定位
→ 再实施修复
```

不得直接猜根因或盲改。

探针规则：

- 使用中文前缀；
- 字段和结果使用中文；
- 高频事件不得进入普通日志；
- 临时探针与正式日志必须区分；
- 临时探针修复后不能擅自删除；
- 需列出待删除项，经确认后下一轮删除；
- 有长期价值的探针可以转为正式诊断功能。

## 六、日志规范

### 高频链路

以下高频事件不得进入普通日志：

- PointerMoved；
- Hover；
- DragPreview；
- RenderFrame；
- 高频 Resize；
- 高频状态刷新。

### Preview / Commit 原则

- Preview：只更新场景预览和渲染；
- Commit / Cancel：才更新 WorldState、Inspector、Diagnostics 等重负载状态。

禁止高频交互直接刷新重型 UI 或诊断系统。

## 七、测试与验证规范

### 1. 测试修改原则

- 实现不符合需求：修实现；
- 需求或公共契约明确变化：可同步修改测试；
- 测试本身错误：必须提供证据；
- 禁止迁就测试；
- 禁止弱化断言；
- 禁止删除失败用例；
- 删除、跳过、禁用测试必须事前请示。

最终报告必须分别列出：

- 实现变化；
- 测试变化。

### 2. 分层验证要求

#### 文档任务

验证：

- 格式；
- 链接；
- 内容一致性；
- 文件引用；
- 事实准确性。

#### 普通代码任务

验证：

- Restore；
- Build；
- 相关测试；
- 警告数量。

#### UI / 输入任务

验证：

- Build；
- 启动；
- 真实交互；
- 未受影响功能回归。

#### Vulkan / 生命周期任务

验证：

- Build；
- 真机运行；
- Resize；
- Present；
- 窗口关闭；
- 资源释放顺序；
- 重建与恢复。

#### 存档 / 场景任务

必须验证：

```text
保存
→ 关闭
→ 重开
→ 数据一致
```

#### 性能任务

必须说明：

- 测量场景；
- 修改前结果；
- 修改后结果；
- 未覆盖范围。

### 3. 人工与真机测试清单 IPO 规范

凡人工测试、真机验收、截图验收或需要用户照做的测试项目，必须写成可执行的 IPO 清单。

每个测试项目必须具备：

- 序号；
- 路径；
- 输入 I；
- 过程 P；
- 输出 O。

标准格式：

```markdown
#### 测试项目：<中文名称>

- 序号：<编号>
- 路径：<当前 UI 的真实中文路径>
- 输入 I：
  - <测试开始前的状态、数据和输入条件>
- 过程 P：
  1. <第一步>
  2. <第二步>
  3. <第三步>
- 输出 O：
  - <能够通过画面、状态、日志或数据明确判断的结果>
```

路径必须使用当前 UI 的真实中文名称，例如：

```text
聚焦
查看全部
平移
环绕
移动
旋转
缩放
选择
框选
```

禁止在人工或真机清单中用内部英文名替代界面文字，例如：

```text
Frame Selected
Frame All
Orbit
Pan
Dolly
```

以下写法无效：

```text
测试 Orbit 是否正常
操作一下 Frame All
测试 Pan
结果：正常
```

输出 O 必须能由画面、状态、日志或数据明确判断，不得只写“正常”“通过”“无问题”。

### 4. 失败处理

Build 或测试失败时：

- 必须依据真实错误和日志修复；
- 最多连续尝试两轮；
- 两轮后仍失败，或修复需要明显扩围时，立即停止；
- 报告事实、疑点、当前工作区状态和下一步建议；
- 不得无限循环试错。

当 Build 明确因本工作区正在运行的 `XuanYu.Editor.App` 锁定输出 DLL 而失败时，AI 必须先核对进程名、PID、启动时间和工作区关联，再自行终止该玄域编辑器进程并重跑原验证命令。不得终止身份不明、其他工作区或与本任务无关的进程；无法确认归属时必须请示用户。

## 八、异常处理规范

允许调整异常策略，但必须满足：

- 禁止空 `catch`；
- 可恢复异常必须记录中文上下文；
- 可恢复异常必须进入明确降级路径；
- 不可恢复异常必须快速失败；
- 失败时必须正确释放资源；
- 生命周期、渲染、存档、数据一致性异常不得静默吞掉；
- 禁止异常后继续使用不可信状态。

最终报告必须说明：

- 触发条件；
- 处理方式；
- 失败后状态；
- 是否降级；
- 是否影响其他模块。

改变跨模块异常语义必须事前请示。

## 九、存档与数据兼容

- 所有持久化数据必须有 Schema 版本；
- 新增可选字段且有安全默认值，可直接处理；
- 删除字段、改字段含义、类型、单位、坐标系、序列化格式，必须事前请示；
- 必须说明旧数据如何读取；
- 必须说明迁移失败如何处理；
- 必须提供回滚思路；
- 禁止旧数据读取失败后静默重置；
- 禁止未经确认覆盖或丢弃旧数据。

## 十二、Git 规范

### 1. Commit

- 每个 Commit 应是独立可验证步骤；
- 真机修复应新增 Commit；
- 不得为了保持历史“漂亮”而覆盖已测试提交；
- 硬件验收失败后继续新增修复 Commit；
- 禁止默认修改已推送历史。

### 2. Push

自动验证通过并完成本地 Commit 后，必须 Push 到 GitHub 远端当前工作分支，作为多电脑开发的远端备份基线。

Push 规则：

- 默认 Push 当前工作分支到其跟踪远端分支；
- 不得因“未进入 main”而跳过 Push；
- Push 前必须确认 worktree、staged、untracked 状态；
- Push 后必须在最终报告中写明远端分支、Push 结果和 HEAD Hash；
- Push 只代表备份和同步，不代表正式封版。

以下操作仍然必须经用户明确确认：

- 合并到 `main`；
- 创建 Pull Request；
- 创建或移动 Tag；
- 创建 GitHub Release；
- 强推、Rebase、重写历史。

### 3. 分支

允许：

- 读取当前分支；
- 查看状态；
- 查看远程差异；
- 明确任务要求时创建和切换新分支。

主里程碑分支规则：

- Git 开发分支必须跟随主里程碑切换；
- 进入新的 `ARCH`、`WORLD`、`QZ` 等主阶段时，应从上一里程碑已验收且工作区干净的 HEAD 创建对应新分支并推送；
- 禁止长期沿用语义已经过时的旧里程碑分支承载新主阶段开发；
- 不得为换分支改写历史、force push、移动已有 commit 或删除旧分支；
- 子阶段 `R1 / R2 / R3` 默认不单独换分支，除非用户明确要求或阶段语义已经进入新的主里程碑。

禁止擅自执行：

- 合并；
- Rebase；
- 删除分支；
- 强推；
- 重写历史。

## 二十、最终执行口径

AI 必须遵循以下判断顺序：

```text
是否违反绝对红线？
├─ 是 → 禁止执行
└─ 否
   ↓
是否属于重大决策？
├─ 是 → 提案并请示
└─ 否
   ↓
是否局部、可验证、可回退？
├─ 是 → 直接完成
└─ 否 → 缩小方案或报告风险
```

最终原则：

> 严格守住边界，但不得失去主动性。  
> 普通问题直接解决，重大问题才请示。  
> 不盲改、不造假、不掩盖、不扩围。  
> 所有结果必须可验证、可回退、可审计。

## 二十一、唯一坐标事实

- 玄域 World Space 固定为右手系、`+Z` 向上、XY 为水平面，正旋转遵守右手规则。
- 世界 X/Y 是固定水平轴，但不得定义“世界唯一 Forward”；Camera、Object Local、Asset Import 与 Geographic Tangent 的 Forward 必须分别声明。
- Transform、Camera、Spatial、Picking 与 Gizmo 必须消费同一 World / View / Projection 事实，禁止形成 Render World 与 Picking World。
- Vulkan 裁剪空间差异只能在 Render Boundary 转换，不得用交换轴、额外负号或临时补丁污染 World、Transform、Picking、Spatial 或 Gameplay。
- 全球地理坐标必须经过显式 Datum、全局双精度、Region 局部、Camera-relative 与 Vulkan float 边界；禁止把整个地球表示成单一 float3。

## 二十二、工具状态与 History 事实

- `ActiveTool` 只能表示持续编辑工具，不得混入 Toggle、一次性 Command 或视图命令。
- `Snap` 等开关必须作为独立 Toggle 状态；点击开关不得改变当前编辑工具。
- 撤销、重做、聚焦等命令不得污染 `ActiveTool`，执行后工具高亮、右上角工具文本和底部工具文本必须保持同源一致。
- 视口 Gizmo 可见性必须对应当前 `ActiveTool` 的真实可操作能力；未实现工具不得显示其他工具的 Gizmo，禁止“看得见但不能用”的伪能力。
- PointerDown 创建交互 Session 时，`SessionTool` 必须由当时唯一 `ActiveTool` 快照生成；Session 创建后可锁定该工具到 Commit / Cancel，但不得读取旧缓存或默认模式。
- 未实现真实 Transform 能力的工具不得伪装完成；Rotate / Scale 未实现时不能偷偷执行 Move Session。
- Undo 必须恢复已提交的 Before Snapshot，Redo 必须恢复已提交的 After Snapshot；二者不得重新模拟输入 Delta。
- Undo / Redo 不得产生新 History；任何新 Commit 必须清空旧 Redo Branch。

## 二十三、Global World 与 Entity Registry 事实源

- 正式实体身份只能使用既有 `EntityId`；禁止为同一实体发明第二套长期 ID、UI ID、Render ID 或 Registry Key。
- 运行期 `EntityId` 默认单调递增，Destroy 后不得立即复用旧 ID；禁止为避免简单计数而引入 GUID 或复杂分布式 ID。
- `GlobalWorld -> EntityRegistry -> Entity State` 是实体生命周期唯一事实源；UI、Renderer、Hierarchy、Inspector、Snapshot、Picking、Gizmo 只能读取、投影或缓存派生快照，不得拥有第二份正式实体真相。
- `EntityRegistry` 的最小正式入口为 `Create`、`Destroy`、`Get`、`TryGet`、`Exists`；销毁已不存在或非法实体必须稳定失败，不得污染 Registry。
- 1000 实体冒烟必须覆盖创建、查询、删除、重复删除、稳定 key、缺失 key 与无污染，并记录创建时间、查询时间和内存变化基线；基线只作观察，不作为未审计性能门槛。
- Partition、Spatial Index、Organization、Terrain、Streaming、Gameplay 或 ECS 接入时，必须消费 `GlobalWorld / EntityRegistry` 的实体事实，不得反向成为实体生命周期 Owner。
- `SceneStateOwner` 只能承担 Scene 投影、编辑会话、Snapshot 聚合和派生空间索引维护；Transform Commit、Undo、Redo、Destroy 必须写回或查询同一个 `GlobalWorld / EntityRegistry` 实体事实，不得维护第二份正式 Transform。
- 自第二十六条起，`SceneStateOwner` 的派生空间索引维护列为受控架构债务（双轨索引：`SceneStateOwner._spatialIndex` 与 `WorldQuery._index` 并存）；ARCH-WORLD-R2 必须收敛为 `GlobalWorld → 唯一 SpatialIndexOwner → WorldQuery`，收敛前禁止为该旧索引新增消费者，收敛后该职责移除。

## 二十四、World Query 与 Spatial Index 事实边界

- `GlobalWorld` 仍是 Entity、Position、Activity 与生命周期唯一事实源；
- `WorldPartition` 只维护 Region Membership 管理事实；
- `SpatialIndex` 只能作为派生查询加速结构，理论上必须可从 `GlobalWorld` 当前状态重建；
- 正式 `World Query` 路径不得通过遍历 `GlobalWorld.Entities` 或 Registry 全扫实现；
- 自动测试可以使用 O(N) 暴力扫描作为正确性 Oracle，但生产查询路径不得依赖该方式；
- `QueryRadius`、`QueryBounds` 等 World Query API 必须返回 `EntityId` 集合，调用者再回到 `GlobalWorld` 查询正式 Entity State；
- Entity Position 正式提交后，必须保持 `GlobalWorld Position Commit → Partition 派生更新 → SpatialIndex 派生更新` 的顺序；
- Region 解决管理 / Activity / Streaming 边界，Spatial Cell / Node 解决查询加速；禁止把 `Region == Spatial Cell` 写成长期架构约束；
- 当前阶段禁止借 Spatial Index 引入 Organization Graph、Terrain、GIS、完整 Streaming、Persistence、ECS 重构、GPU Driven Renderer 或 Octree 大工程。

## 二十五、编辑器可见文本与树形 UI 边界

- 运行期用户可见日志不得使用 `ARCH-*`、`WORLD-*` 等阶段代号作为模块名；阶段代号只允许出现在 changelog、报告、测试、审计元数据或开发注释中。
- 日志表格必须以时间作为第一视觉字段，并保持“时间 / 级别 / 来源 / 模块 / 消息 / 详情”的阅读顺序。
- 普通用户日志必须优先使用中文显示文本；Vulkan、API、DPI、HWND、GPU 型号等标准名称可以保留。
- 高频诊断和内部函数名不得直接进入普通 UI 日志；确需保留的低频诊断必须转为中文阶段、中文字段和可解释详情。
- Project Tree 与 Hierarchy Tree 必须保持同一视觉语言：缩进、分支线、行高、悬停、选中态和矢量路径图标一致。
- 树与 Inspector 的用户可见名称必须使用中文显示映射；不得因为 UI 中文化改名而重命名内部 C# 类型、实体 key 或长期公共 API。

## 二十六、物理分层归属与身份边界

- Core 极度克制：`XuanYu.Core` 只保留稳定身份（`EntityId`）、数学基元（Vector3d / Aabb3d / Ray3d / 几何求交）、时间（SimulationTime）、结果（EngineResult）与极少量真正全局基础诊断契约；不得新增 World、Scene、Viewport、Picking、Gizmo、Camera、History 或 Transform Session 类型。
- World 拥有世界与空间事实：`GlobalWorld / EntityRegistry / Region / Partition / SpatialIndex / WorldQuery / SceneStateOwner` 等“世界里有什么、在哪里”的正式事实归属 World 层（目标程序集 `XuanYu.World`），不得挤在 Core。
- WarCore 拥有战争语义（未启动）：军事身份、编制、阵营等战争领域语义未来归属 `XuanYu.WarCore`；在“奇正相生·一个士兵闭环”正式启动前，不得创建空接口或空程序集。
- 唯一权威事实禁止双轨复制：同一类世界事实只能有一个权威载体；空间索引全引擎唯一（`GlobalWorld → 唯一 SpatialIndexOwner → WorldQuery`），Scene、Picking、Render 不得各自维护第二套“谁在哪里”的索引。
- 稳定身份与临时句柄必须分离：`EntityId` 是纯稳定身份，不得混入 Generation / Revision；未来存储槽复用防 stale 由 `EntityHandle`（Index + Generation）承担，状态版本由 `EntityRevision` 承担，三者不得合并。
- 术语统一：正式实体身份术语只使用 `EntityId`，不再使用 `EntityKey` 第二套叫法。
- 依赖禁区：`Core → World / WarCore / Editor / Vulkan` 禁止；`World → WarCore / Editor / Vulkan` 禁止；`WarCore → Editor / Vulkan` 禁止。
- Viewport Picking 固定三层拆法：Ray / AABB 数学在 Core，空间查询在 World，`ViewportPickingService` 在 Editor。
- `SceneRenderSnapshot` 等 Snapshot 是派生表现数据的边界 DTO，不是 World Truth；禁止携带"没有相机就创建编辑器默认相机"之类的隐藏后门，相机只能由 Editor/View 以 `CameraState` 传入。
- `XuanYu.Editor` 拥有编辑操作会话规则（Begin / Preview / Commit / Cancel、构图、相机操作算法），但不得拥有实体永久位置；Editor 不得依赖 Avalonia 或 Vulkan 实现，不得成为第二套 World 真相；Editor 最终写入必须经过 World 权威入口（`SceneStateOwner` → `GlobalWorld`）。
- 物理分层治理按 `ARCH-WORLD-R0 → R5` 小步推进（裁定见 `docs/arch-world-layer-attribution.md`），每轮独立验收，禁止大爆炸式迁移。

## 二十七、.NET 构建、测试与子进程生命周期治理

> 本章程因 WORLD-B-R4 收口期出现“dotnet 构建子进程残留持锁、验证代理无限等待、changelog 提前写通过”的治理缺口而设立（GOV-DOTNET-R1，v0.2.20.11-fix）。以下条款为不可违反原则，与第七章验证规范互补；冲突时以本章程为准。

### 1. 构建与测试必须串行

- 同一仓库内，不得同时运行两个及以上的 `dotnet restore` / `dotnet build` / `dotnet test` / `MSBuild` / `vstest` / `testhost`。
- 前一个命令未返回明确退出码之前，不得启动下一个命令。
- 禁止为“节省时间”并行运行解决方案构建、多个测试项目和架构门禁。

### 2. 默认使用稳定验证模式

- AI 执行正式构建和测试时，默认优先保证生命周期可控，而非追求最高并行速度。
- 验证开始前必须执行 `dotnet build-server shutdown` 并设置 `$env:MSBUILDDISABLENODEREUSE = "1"`；验证结束必须再次执行 `dotnet build-server shutdown`。
- 正式构建默认使用：`dotnet build <方案> -m:1 -nr:false -p:BuildInParallel=false -p:UseSharedCompilation=false`（单一工作节点、禁节点复用、禁项目并行、禁共享 Roslyn 编译服务器）。

### 3. 解决方案只完整构建一次

- 一次正式验证链中，解决方案只允许完整构建一次。
- 构建成功后，测试必须使用 `dotnet test <测试项目> --no-build --no-restore`，禁止每运行一个测试项目就再次隐式构建整个依赖链。

### 4. 每条命令必须有生命周期记录

- 每条正式门禁命令必须记录：完整命令、开始时间、结束时间、退出码、关键输出、是否超时、是否被取消。
- 不得只记录“运行过”，必须记录明确结果。

### 5. 超时与无输出规则

- 默认：单条命令最长 5 分钟；连续无新输出 2 分钟。
- 超过任一限制，立即停止等待并报告当前状态，不得重复循环。
- 性能 / 压力测试等确需更久的命令，必须执行前明确预计时长，并由当前轮计划单独批准。

### 6. 取消必须覆盖完整进程树

- 取消构建或测试时，必须同时终止该命令创建的完整子进程树：`dotnet.exe` / `MSBuild.exe` / `testhost.exe` / `vstest.console.exe` / `VBCSCompiler.exe`。
- 若执行环境无法确认或终止子进程，必须立即停止本轮验证，不得再次启动任何 `dotnet` 构建或测试。
- 禁止在旧进程状态未知时反复重试。

### 7. 环境失败不能伪装成代码失败

- 出现 `Access is denied` / `UnauthorizedAccessException` / 文件正被另一进程使用 / 无法写入 obj/bin / 无法删除 apphost.exe / 无法覆盖测试 DLL 时，优先判定为环境阻断。
- 在未出现明确 C# 编译错误、类型错误或测试断言失败前，不得宣称代码错误。
- 也不能宣称代码已通过，只能记录“构建未完成，当前被环境阻断”。

### 8. 禁止用删除 obj/bin 代替释放进程

- 文件可能仍被进程占用时，不得直接删除 `obj/` 或 `bin/`，不得把清空生成目录当作释放文件锁的方法。
- 必须先结束占用进程；只有确认不存在残留构建 / 测试进程后，才允许在确有必要时清理生成目录。

### 9. 受安全策略限制时停止，而不是绕过

- 若沙箱安全策略阻止 `tasklist` / `Stop-Process` / 进程枚举 / 进程树终止，AI 不得尝试其他 LOLBin、旁路命令或危险方式绕过。
- 正确处理：报告限制 → 停止继续执行 → 请求用户手动清理进程或重启环境 → 等待环境恢复后再验证。

### 10. 重试必须有前提变化

- 同一失败命令不得原样重复运行。
- 只有在以下条件之一真实发生后，才允许重新执行一次：用户已结束残留进程 / WorkBuddy·IDE·测试运行器已关闭 / 电脑已重启 / 目录权限已修复 / 安全软件占用已解除 / 构建参数已按批准方案调整。
- 环境无变化，不得把重复执行当作排查。

### 11. changelog 与验收报告必须真实

- `changelog.md`、验收报告和最终回复中的门禁结果，只能来源于当前开发轮、当前仓库状态、当前实际执行命令和当前明确退出码。
- 不得直接复制或采信上一会话写入的“构建通过 / 测试通过 / 架构门禁通过”。
- 当前轮未重新执行，必须写“本轮未复证”；被环境阻断，必须写“环境阻断，未取得有效验证结果”。
- 禁止先在 changelog 写“已通过”，再补跑验证。

### 12. 提交与推送门禁

- 运行时代码或测试发生修改时：`静态门禁通过 → 构建通过 → 测试通过 → 必要真机验收 → commit → push`。
- 构建或测试被环境阻断，默认不得把实现宣布为完成。
- 纯文档治理轮（无运行时代码变化）不必为形式完整而跑全解决方案构建，但必须完成：`git diff --check` / 5+100 / 版本源一致性 / Markdown 结构核对 / 修改范围核对 / 架构守卫一次 / commit / push / 远端 tip 复核。

## 二十八、开发轮流程与关键路径治理

> 本章因 WORLD-B-R4 收口期暴露“目标不冻结即扩围、调查无限考古、快速验证滞后、文档对账拖慢落库、自动测试通过即误判功能 CLOSED”等流程问题而设立（GOV-FLOW-R1，v0.2.20.13-fix）。以下条款为不可违反原则，与第二十七章生命周期治理互补；冲突时以本章与第二十七章共同约束为准。

### 1. 每轮先冻结目标

每个开发轮开始时，必须明确写出：

- 主要目标：最多 3 项；
- 允许修改范围：列清单；
- 验收门禁；
- 停止条件；
- 明确禁止事项。

发现的新问题只有符合以下任一情况才能立即扩大范围：

- 会导致错误实现；
- 会破坏架构边界；
- 会造成审计结果失真；
- 会使本轮功能无法成立。

普通文档措辞、历史漏登记、非阻断视觉偏好，不得拖慢当前主线。

### 2. 固定有限状态流程

代码开发轮必须按以下状态推进，不得在状态之间来回反复：

```text
调查
→ 实装
→ 针对性快速验证
→ 正式完整门禁
→ 最小文档同步
→ commit + push
→ 等待用户验收
```

一旦进入 `commit + push`，禁止继续增加功能或重新展开全仓库审计。

### 3. 根因链闭合后停止调查

调查只需要回答：

- 问题在哪里产生；
- 经过哪些合同传递；
- 最终在哪里表现失败；
- 哪些测试遗漏了该链路。

根因链闭合后必须停止搜索，不得继续进行无目标的全仓库考古。

### 4. 快速验证必须前置

禁止大量修改完成后才第一次编译。应按影响层分段验证：

- 修改合同 → 编译相关项目；
- 修改 Vulkan / Shader → 编译渲染项目；
- 修改交互 → 运行相关测试；
- 最后统一执行一次正式完整门禁。

快速验证不能代替正式门禁，但必须用于尽早发现漏 `using`、签名不一致和合同错误。

### 5. 正式门禁只执行一次有效链

正式验证使用第二十七章 GOV-DOTNET 稳定模板：

```text
完整 build
→ 相关测试
→ 架构守卫
```

全部串行。只有代码再次发生实质变化，才重新执行受影响的验证。仅修改 changelog、版本号或准确描述时，不应无意义重跑完整构建。

### 6. 正确使用并行

允许并行：

- 多个互不依赖的只读搜索；
- 不同文件的只读检查；
- 独立证据收集。

禁止并行：

- 两个 `dotnet` 构建或测试；
- 同一个文件的多个写入操作；
- Git staging、commit、push；
- 可能修改同一状态源的任务。

原则：该并行的调查并行，不该并行的写入严格串行。

### 7. 文档只做本轮必要同步

每轮只同步：

- 本轮真实版本号；
- 本轮真实 changelog；
- 新增、删除、移动、重命名或职责变化对应的 file-tree；
- 本轮新形成并经用户确认的长期治理规则。

禁止为了“完整”顺手全面清理历史文档。旧的小问题可以登记，留到后续正常开发轮顺手修正。

### 8. 代码与验证完成后立即落库

当以下条件满足：

- 目标代码完成；
- 针对性测试通过；
- 正式门禁通过；
- 必要文档同步完成。

必须立即：

```text
git diff --check
→ commit
→ push
→ 远端 tip 复核
→ 工作区 clean
```

不得等用户再次催促后才执行已经具备条件的 commit 和 push。

### 9. 减少过程性废话

执行过程中只在以下节点汇报：

- 发现真实阻断；
- 完成实装；
- 正式门禁结束；
- commit / push 完成。

禁止每执行一条小命令就暂停并长篇说明“接下来做什么”。工具可以连续完成一个已批准的操作批次，再一次性汇报。

### 10. 必须定义停止条件

开发轮停止条件必须在开工前冻结，例如：

- 代码与测试全绿；
- 必要文档完成；
- commit + push 完成；
- 远端 tip 等于本地 HEAD；
- 工作区 clean。

达到后必须停止修改，等待用户真机验收。不得在等待验收时主动开始下一阶段。

### 11. 当前阶段未验收，不得启动后续阶段

如果当前轮需要真机验收：

```text
自动测试通过 ≠ 功能正式 CLOSED
```

只有用户明确确认真机通过后，才能关闭阶段并规划下一阶段。

宪法案例（WORLD-B-R4）：WORLD-B-R4 真机验收未通过前，禁止启动 F5 缩放；真机未通过即宣布 CLOSED 视为违反本章。

### 12. 交付速度与审计真实性同等重要

严格治理不能被误解为无限审计。执行 AI 必须同时保证：

- 不跳过真实门禁；
- 不伪造验证结果；
- 不扩大无关范围；
- 不延迟已具备条件的落库；
- 不以“继续核对”为由无限拖延。

### 13. 同一文件禁止并行编辑

任何单个文件在同一开发轮内，不得由多个并行操作同时写入。需要修改同一文件时，必须串行：先完整读取、再单次精确修改、再核对结果。禁止把同一文件的多次改写拆给并行任务。

### 14. 落库后进入等待验收状态

`commit + push` 完成且远端 tip 复核通过后，本轮正式结束，进入等待用户验收状态：

- 不得主动开始下一阶段开发；
- 不得在未获用户验收结论前启动后续功能（如 F5）；
- 不得在等待期顺手扩展、重构或补账历史文档；
- 用户明确验收或下达新指令前，保持静默。

### 15. 宪法案例：WORLD-B-R4 真机未过禁止 F5

WORLD-B-R4 旋转工具闭环经真机验收判定 **FAIL**（旋转环尺寸不合适、旋转目标疑似与选中实体不同步有延迟感、缺少旋转交互日志、变换工具激活时不能直接点选其他实体切换 Gizmo、选中缺少 Blender 式轮廓高亮）。该缺陷清单登记于 changelog，保留到 GOV-FLOW-R1 治理轮结束后处理。

在以下结论之一出现前，任何执行 AI 都不得：

- 宣布 WORLD-B-R4 CLOSED；
- 启动 F5 缩放功能；
- 把“自动测试全绿”当作“功能 CLOSED”的依据。

只有用户明确确认真机通过后，才允许关闭 R4 并进入 F5。

## 二十九、开发里程碑与轮次代号规范

本规则自 `WORLD-C-R4` 起生效，历史记录不追溯重命名。章节编号按现有结构顺延，不为插入本规则重排历史章节。

### 1. Milestone：主里程碑

主里程碑表示一段较大的产品或架构建设阶段，例如：

```text
WORLD-C
WORLD-D
WARCORE-A
```

主里程碑内部可以包含多个能够独立完成、验收和关闭的正式开发轮次。

### 2. R：Round，正式开发轮次

`R` 只允许表示 `Round`，即能够独立定义目标、边界、验收条件并最终标记为 `CLOSED` 的正式开发轮次，例如 `WORLD-C-R4`。

每个 Round 必须具备：

- 明确的产品目标；
- 明确的纳入范围；
- 明确的排除范围；
- 自动门禁；
- 真机验收标准；
- 独立收口结论。

禁止把普通代码提交、修复批次或验收次数命名为新的 `R`。

### 3. D：Development，正常开发步骤

`D` 表示某个 Round 内部的正常开发步骤，例如：

```text
WORLD-C-R4-D0
WORLD-C-R4-D1
WORLD-C-R4-D2
```

通常 `D0` 用于审计、合同、依赖和边界冻结；`D1` 及以后用于正式功能实现。`D0` 不是每个 Round 的强制形式，只有涉及新 Schema、新依赖、新资产边界或重要架构决策时才需要设置。

普通开发过程中发现并修正的问题，只要尚未进入正式验收阶段，仍然属于当前 `D`，不得滥用 `F`。

### 3.1 I：Implementation，可选实施切片

`I` 表示某个 `D` 内部的可选实施切片。**`I` 不是强制阶段，默认规则是一个 `D` 应优先一次完成**，不得为了流程完整、文档漂亮或降低单轮工作量而机械拆分。

只有同时满足以下全部条件，才允许使用 `I`：

1. `D` 存在真实、独立的技术边界；
2. 单轮实现会显著增加数据损坏、架构越界或无法回滚的风险；
3. 每个切片都能独立验证；
4. 开发计划已明确批准拆分，或用户明确同意。

禁止：

- 每个 `D` 默认拆成 `I1 / I2 / I3`；
- 为普通文件修改创建 `I`；
- 为了延长流程创建 `I`；
- 一个简单功能拆成多个实施切片。

正确示例（具有真实独立风险的切片）：

```text
WORLD-C-R4-D4-I1：托管资源事务内核
```

`I` 完成后，同一 `D` 的剩余功能应继续在同一开发轮完成，不得继续机械拆分。

### 3.2 防止过度拆分

- 不得把管理编号本身当作开发成果。阶段编号服务于真实工程边界，不得反过来迫使一个能够一次完成的功能被拆成多个轮次。
- 当自动测试、架构边界和回滚能力足以控制风险时，应优先在同一开发轮完成同一 `D` 的全部实现，避免人为延长主线。
- 从本规则生效后，新产生的 `D` 内部编号只允许使用 `I` 表示已经明确批准且真实独立的风险切片；其余工作直接归属 `D` 本身。


### 4. A：Acceptance，真机验收批次

`A` 只表示用户或指定验收者执行的正式真机验收，例如：

```text
WORLD-C-R4-A1：PASS
WORLD-C-R4-A1：FAIL
```

自动测试、构建、架构守卫、静态检查和代码审计属于自动门禁，不得命名为 `A`。只有真机验收 PASS，且自动门禁和仓库状态同时满足收口要求，Round 才能宣布 `CLOSED`。

### 5. F：Fix，验收缺陷修复批次

`F` 只用于正式验收后发现真实问题，需要追加代码修复的情况。标准链路：

```text
WORLD-C-R4-A1：FAIL
WORLD-C-R4-F1：完成修复
WORLD-C-R4-A2：PASS
WORLD-C-R4：CLOSED
```

正常开发尚未完成、自动测试首次暴露实现错误、普通编译错误、开发过程代码调整、文档措辞修正和尚未交付真机验收的候选版本，均不得命名为 `F`，仍归属当前 `D`。

### 6. CLOSED：轮次状态

`CLOSED` 是 Round 的最终状态，不是新的开发层级，也不使用单独字母代号。正确写法为：

```text
WORLD-C-R4：CLOSED
```

不得写成 `WORLD-C-R4-C1`、`WORLD-C-R4-RC`，除非未来另行制定正式发布候选规则。

### 7. 禁止重复使用 R

从本规则生效后，禁止产生 `WORLD-C-R4-R1`、`WORLD-C-R4-R8` 等双 `R` 命名。尚未开始实施的 R4 子轮必须改为 `WORLD-C-R4-D1`、`WORLD-C-R4-F1` 或 `WORLD-C-R4-A1` 等真实性质名称。

已经完成并落库的历史名称，例如 `WORLD-C-R3-R8`，继续作为历史审计事实保留，不批量重命名历史提交、历史报告、历史版本、已关闭验收记录或已发布文档。
