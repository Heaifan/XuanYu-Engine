# XuanYu Engine 代码宪法

创建时间：2026-06-10
最后更新：2026-08-26（新增多 Agent 与子代理开发宪则）

本文档定义 XuanYu Engine 的代码硬性规则（历史代号 FluidWarfare）。

## 单一职责

每个文件、类和方法都应该只有一个清晰存在理由。

不要在同一个实现单元里混合 UI、数据读取、模拟、渲染、平台适配、日志和领域计算。

职责不清时，先拆清领域边界，再写实现。

## 文件长度

普通代码文件建议不超过 100 行。

复杂基础设施文件在职责单一时可以接近 150 行。

超过 150 行前必须先提出拆分方案。

超过 200 行的文件必须有明确理由。

超过 300 行的文件默认禁止。

## 目录规模

一个目录通常应少于 7 个文件。

超过 10 个文件时必须按领域或职责拆分二级目录。

不得创建泛化的工具、辅助、总管或处理器目录。

目录拆分必须按领域概念进行，而不是按文件编号进行。

## 明确命名

名称必须描述具体职责。

可接受示例包括：

1. `ScenarioEntityLoader`
2. `CombatContactResolver`
3. `MoraleDeltaCalculator`
4. `VulkanSwapchain`

## 中文化规则

机器读取的标识保持英文，人类读取的文本使用中文。

必须使用中文的内容包括：

1. `EngineError.Message`
2. 异常 message。
3. 日志 message。
4. 编辑器提示。
5. 导出提示。
6. 验收结果。
7. `file-tree.md`。
8. `CHANGELOG.md`。
9. 开发任务说明。

必须保留英文的内容包括：

1. 命名空间。
2. 类名。
3. 方法名。
4. 文件名。
5. 测试方法名。
6. `EngineError.Code`。
7. 程序内部枚举名。

示例：`Core.InvalidArgument` 作为错误代码保持英文，`参数无效。` 作为错误信息使用中文。

## 平台隔离

Core、ECS、Simulation、World、Combat、AI、Data 和 Render 抽象项目不得依赖 Windows、Android、Avalonia 或具体 Vulkan 实现。

平台相关代码只能位于 Runtime、Editor、Exporter 或具体渲染后端。

## 旧仓库隔离

FluidWarfare-old 只作为历史参考。

新引擎代码不得复制旧代码、旧 OpenGL 实现、旧工程布局或旧前缀命名。

旧仓库中的思想可以被重新表达。

旧仓库中的实现不得被直接迁移。

## Vulkan 返回值规则

除规范明确返回 void 的 Vulkan 函数外，所有 Result 必须被保存并分类处理。
禁止直接丢弃 VkResult。

## 两阶段枚举规则

所有 count → array 的 Vulkan 枚举必须处理 Incomplete，并设置有限重试次数。

## 等待规则

Editor UI 线程不得使用 ulong.MaxValue 等无限 Vulkan 等待。
所有 Fence / Acquire 等待必须有上限和超时处理。

## native 资源规则

每个 native 创建入口必须在构造时具备对应销毁能力。
禁止先创建资源、后续再"可选赋值"销毁函数。

## Swapchain 唯一入口

vkCreateSwapchainKHR 与 vkDestroySwapchainKHR 只能由 Scene3D Swapchain 模块调用。

## 生命周期测试

新增 Vulkan 资源类型时，必须同时增加：
1. 创建成功测试
2. 部分失败清理测试
3. Dispose 幂等测试
4. 创建/销毁数量不变量测试

## 多 Agent 与子代理开发宪则

XuanYu Engine 正式鼓励并优先采用多 Agent、子代理和后台任务协同开发。并行开发的目标是提高吞吐、缩短等待时间、扩大独立审查覆盖面，但不得以牺牲正确性、可追溯性和文件所有权为代价。

### 默认优先使用多 Agent

中型及以上任务开始前，主 Agent 必须判断是否存在两个或更多能够独立推进的工作流。

只要任务可以安全拆分为实现、测试、打包、调查、文档、审计等相互独立的职责，就应优先使用多个 Agent 或子代理并行推进。

跨模块开发、多个独立 TODO、实现与测试可并行、存在长时间安装/构建/文件操作等待时，默认应使用多 Agent 或后台任务提高利用率。

单 Agent 串行包办不再作为复杂任务的默认工作方式。只有任务足够小、不可合理拆分，或拆分成本明显高于收益时，才允许单 Agent 完成。

并行是手段，不是 KPI。存在真实前后依赖的 Build → Package → Manifest → Gate 等链路必须保持串行，不得为了形式上的并行制造竞态。

### 主 Agent 是唯一集成负责人

每个多 Agent 任务必须存在一个主 Agent，承担 Tech Lead / Integrator 职责。

主 Agent负责：维护统一 TODO、拆分职责、分配文件所有权、协调子代理、处理中断和冲突、集成结果、执行最终构建和门禁、输出最终报告。

主 Agent 不应重复子代理已经完成的调查和实现，也不得在子代理仍持有文件所有权时并发修改同一文件。

子代理发现跨域问题时，应报告给主 Agent，由主 Agent重新分配或明确移交所有权，不得自行扩大范围。

### Agent 级单一职责

代码 SRP 同样适用于 Agent。

一个子代理应拥有清晰、可描述、可验收的单一职责域，例如 Runtime、Packaging、Tests、Gallery、Documentation、Review，而不是泛化的“把剩下的都处理掉”。

任务拆分优先按模块、目录和文件所有权划分，不按模糊功能描述随意拆分。

每个写入型 Agent 必须知道自己允许修改的文件范围和禁止修改的范围。

### Single Writer Rule

同一时刻，一个可写文件只能有一个明确 owner。

禁止两个 Agent、两个后台任务或 Agent 与后台任务同时写入同一文件、目录产物或共享可变输出。

共享文件默认由主 Agent 或被明确指定的唯一 owner 修改。

需要转移所有权时，必须先停止旧 Agent / 旧后台任务，确认其不再写入，再由新 owner 接管。

发现旧任务建立在已废弃假设上时，应立即终止 superseded job，不得让过时任务继续污染工作区。

### 合理利用子代理能力

主 Agent 应先检查当前可用的 Agent / Subagent Provider，再按任务特点选择合适的执行者，不得假设某个 provider 必然存在。

持续数轮的独立职责优先使用可继续对话的 continuable 子代理，避免反复创建失去上下文的一次性 Agent。

代码实现、测试、调查、审查可根据 provider 擅长方向分配。条件允许时，最终独立审计应优先使用与主要实现不同的 Agent / provider，以减少同源盲区。

主 Agent 应合理使用当前系统提供的 Agent 列举、消息发送、中断、继续执行和状态查询能力，主动协调，而不是让子代理无人管理地自行扩张。

### 后台任务与并发边界

安装依赖、同步 vendor、文件哈希、独立测试等耗时任务在不存在读写冲突时可以作为后台任务并行执行。

后台任务一旦成为后续构建的输入，必须等待其真实完成后再进入依赖步骤。

禁止构建进程读取仍在写入的 vendor、generated、release、dist 或其他共享产物目录。

后台任务、Agent、构建流程的并发必须建立在独立输入和独立输出上。

### 停止、失败与重新分配

同一问题连续两次尝试失败后，不得机械重复试错。应停止、报告原因，并由主 Agent决定重新分配、缩小范围或采用新的技术路径。

Agent 被中断、任务被取代或方案已经失效后，必须停止继续写入。

任何“旧任务仍运行但新任务已经开始写同一范围”的状态都属于治理错误。

### 独立审计与门禁

复杂任务完成集成后，应尽可能启动一个只读 Review Agent 进行独立审计。

Review Agent 默认不得修改实现文件，只输出 BLOCKER、MAJOR、MINOR、PASS 等审查结果；修复工作回到原 owner 或由主 Agent重新分配。

任何 Agent 都不得把未实际执行的测试或 Gate 标记为 PASS。

受环境、凭据、硬件或外部条件限制而无法执行的门禁，必须明确标记 NOT RUN，并记录原因和所需条件。

多 Agent 并行不得降低现有 0 Warning / 0 Error、测试、架构和验收要求。

### 最终报告与可追溯性

多 Agent 任务的最终报告至少应记录：

1. 主 Agent 与子代理分工。
2. 各 Agent 的文件所有权和实际贡献。
3. 统一 TODO 最终状态。
4. 被中断、重分配或失败的任务及原因。
5. 构建与 Gate 的真实结果。
6. 未执行门禁及原因。
7. 独立 Review 结论。
8. 与原任务规格存在的实施偏差。

多 Agent 开发必须做到“可并行、可中断、可接管、可审计、可复现”。速度提升不能建立在丢失责任边界或验收真实性之上。
