# Agent 正式完成报告规范

> 状态：ACTIVE  
> 生效日期：2026-09-16  
> 适用范围：Codex、Gemini、ChatGPT 及其他参与玄域引擎开发、修复、审计、治理回写的 Agent。

## 1. 目的

正式完成报告必须可复核、可追溯、可与 Git 事实直接对照。禁止只报告“已完成 / 已推送 / 测试通过”而缺少提交、门禁和文件变化证据。

## 2. 强制章节

正式完成报告固定包含以下章节，顺序原则上保持一致：

1. 任务结论 / 当前状态；
2. Git 状态；
3. 本轮实现；
4. 验证结果；
5. 治理 / 经验回写；
6. 修改文件清单；
7. 范围、风险与未完成项；
8. 真机验收状态 / 下一入口。

任一强制章节缺失时，报告状态为 `REPORT INCOMPLETE`，不得作为正式收口报告。

## 3. 任务结论与状态

允许状态：

- `完成`：代码与自动化门禁完成，且不存在额外人工验收要求；
- `待真机验收`：代码与自动化门禁完成，但 UI / 交互 / 视觉仍需用户真机确认；
- `部分完成`：仅完成冻结任务的一部分；
- `阻塞`：存在明确阻塞条件，必须给出证据。

涉及 UI、交互或视觉时，自动测试通过不得替代用户真机验收；用户未验收前不得自行写 `CLOSED`、`最终验收通过`。

## 4. Git 状态

必须报告：

- 分支名；
- 本轮全部 Commit Hash 与 Commit Message；
- 最终 HEAD 完整 Hash；
- 远端同步状态 `ahead/behind`；
- Working Tree 状态。

禁止只写“已推送”而不给 Commit Hash。

## 5. 本轮实现

只列已经实际落地的事项。不得混入候选方案、推测结果、下一阶段计划或未实施的顺手优化。

若本轮明确冻结范围，还必须说明未修改的关键边界，例如 Schema、Selection Model、公共 API、UI 布局、依赖等。

## 6. 验证结果

每个门禁必须给出实际执行结果，例如：

```text
专项测试：16/16 PASS
受影响 Build：0 Warning / 0 Error
ARCH-A：PASS
5+100：PASS
git diff --check：PASS
```

未执行的验证不得写成 PASS。若存在既有失败或环境阻断，必须明确区分 `PRE-EXISTING`、`BLOCKED` 与本轮新增失败。

**5+100 为硬红线，不存在临时豁免、事后再拆或风险接受。**

## 7. 治理 / 经验回写

没有治理回写时写 `无`。

存在回写时必须区分：

- 候选问题证据；
- 已验证 ERR；
- 已提炼 EXP；
- Knowledge / Decision 索引更新。

候选审计材料不得直接当作正式 ERR。

## 8. 修改文件清单

### 8.1 必须按 Commit 分组

每个 Commit 单独列出实际变更文件，禁止把多个提交揉成一个无法核验的文件表。

### 8.2 每个文件必须包含

- 仓库相对路径；
- Git 状态：`A / M / D / R`；
- `+新增行 / -删除行`；
- 文件职责分类：生产代码 / 测试 / 文档治理 / 资源等。

推荐格式：

```text
M  +12 / -3   XuanYu.Editor.UI/Vm/Inspector/InspectorRecentStore.cs
A  +63 / -0   XuanYu.World.Tests/UiRuntime/InspectorPropertyTargetTests.cs
M  +4  / -1   docs/docs-index.md
```

行数统计必须来自 Git 可复核结果（优先 `git diff --numstat <parent> <commit>` 或等价提交统计），不得人工估算。

如果 Git 将文件标记为 modified 但显示 `+0 / -0`、`patch=null` 或 numstat 不可用，不得据此断言“没有文本变化”。必须标记为 `统计不可用`，并注明可能存在二进制判定、编码、换行或其他 Git 无法按普通文本统计的情况；必要时继续核对实际内容。

### 8.3 同一文件跨多个提交

同一文件在多个 Commit 中修改时：

- 必须在对应 Commit 下分别出现；
- 每个 Commit 使用自己的行数统计；
- 最终汇总的“唯一文件数”只计算一次。

### 8.4 汇总统计

报告末尾至少给出：

```text
本轮 Commit 数：2
提交文件记录数：21
唯一文件数：20
新增行：298
删除行：27
净变化：+271
```

“提交文件记录数”与“唯一文件数”不得混为一谈。若存在统计不可用文件，新增/删除总数必须标记为“仅统计 Git 可计数文本文件”，不得伪装成全量精确总数。

## 9. 范围、风险与未完成项

必须明确：

- 是否扩围；
- 是否修改 Schema / 架构 / 公共 API / 依赖；
- 是否存在已知风险；
- 是否存在待真机验收、既有债务或后续独立任务。

若证据显示需要超出冻结范围，Agent 必须停止扩围并请求单独批准。

## 10. 标准报告模板

```text
# Agent 正式完成报告

## 1. 任务结论
状态：完成 / 待真机验收 / 部分完成 / 阻塞
<一句话结果>

## 2. Git 状态
分支：<branch>
提交：
- <hash> — <message>
最终 HEAD：<full hash>
ahead/behind：0/0
working tree：clean

## 3. 本轮实现
- ...

## 4. 验证结果
- 专项测试：x/x PASS
- Build：0 Warning / 0 Error
- ARCH-A：PASS
- 5+100：PASS
- git diff --check：PASS

## 5. 治理 / 经验回写
无 / ERR / EXP / Knowledge ...

## 6. 修改文件清单
### Commit <hash> — <message>
生产代码：
M  +x / -y   path/to/file.cs
测试：
A  +x / -0   path/to/test.cs
文档：
M  +x / -y   path/to/doc.md

汇总：
- Commit 数：x
- 提交文件记录数：x
- 唯一文件数：x
- 新增行：x
- 删除行：x
- 净变化：+x

## 7. 范围 / 风险 / 未完成项
- ...

## 8. 当前状态 / 下一入口
- ...
```

## 11. 审计判定

满足本规范仅代表“报告完整”，不代表实现本身正确。审计方仍需按需要核对 Commit、Diff、测试、门禁和真机结果。
