# 一、规范定位

## 1. 规范性质

本规范不是开发者可以自由参考的建议书，而是：

> **强约束的默认标准，加少量经过审批的受控例外。**

规范条款分为三级：

| 等级 | 含义 | 执行要求 |
|---|---|---|
| 必须 | 项目统一底线 | 违反即不得验收 |
| 应当 | 默认设计方案 | 偏离时必须说明理由并经过审查 |
| 可以 | 规范允许的选择 | 只能在规定范围内选择 |

开发者不得以“视觉偏好”“局部方便”“实现简单”或“与本轮无关”为理由，自行跳过规范。

## 2. 例外机制

专业界面确实无法适用通用规则时，可以申请例外，但必须同时满足：

1. 指出偏离的具体条款；
2. 说明通用规则无法满足的原因；
3. 明确影响模块、界面和边界；
4. 提供替代规则，不能留下无标准区域；
5. 经过 UI 规范审查；
6. 建立专项自动化验证；
7. 完成专项真机验收；
8. 正式登记，不得口头放行。

页面开发者不能自行宣布例外。

## 3. 适用范围

本规范覆盖：

- 玄域引擎编辑器；
- 检查器、地图编辑器、层级树、图层面板；
- 日志、调试工具、开发者控制台；
- 启动器、安装器；
- 游戏内开发和调试工具；
- 《兵无常势》正式游戏 UI。

全项目共享基础可用性门禁，但允许不同领域采用不同艺术表现：

- **编辑器和开发工具**：高信息密度、清晰、稳定、克制；
- **启动器和安装器**：清晰、低操作成本、易于恢复；
- **正式游戏 UI**：允许独立的品牌、美术和世界观表达。

## 4. 文档组织

所有 UI 规则统一写入本文件，不拆分成互相独立的分册。

允许通过章节区分编辑器、游戏、启动器等专项规则，但不得形成相互冲突的多套规范。

# 二、规范发布与旧 UI 整改

## 1. 集中整改原则

本规范正式发布后：

> **暂停新增功能开发，对当前仓库中已经实现的 UI 进行全面审计和集中整改。**

整改未完成前，不进入新的编辑器功能、游戏 UI 或工具面板开发。

本次整改只覆盖当前仓库已经存在的界面，不包含尚未开发的未来 UI。

## 2. 全面整改范围

整改必须覆盖：

- 字号、字体、字重和行高；
- 颜色、背景、边框和对比度；
- 间距、尺寸、圆角和点击热区；
- 图标风格和状态辨识；
- 对齐、布局和信息密度；
- 悬停、选中、焦点和禁用状态；
- 表单、输入和错误校验；
- 滚动、拖动和快捷键；
- 最小窗口、响应式布局和高 DPI；
- 键盘操作和可访问性；
- 日志、错误和操作反馈；
- 加载、空状态和进度；
- 动效、响应速度和性能；
- 自动化测试和真机验收。

## 3. 通过门禁

- 全解决方案必须达到 **0 Warning / 0 Error**；
- 任何 Warning 都是阻塞项；
- 不得以“既有问题”或“与本轮无关”为通过理由；
- 自动化测试与真机验收必须同时通过；
- 自动检查通过不等于视觉验收通过；
- 整改未清零前，阶段不得关闭；
- 规范整改未完成前，不恢复新增功能开发。

# 三、UI Token 体系

## 1. Token 目标

先统一定义基础参数，页面直接引用统一参数，不再重复填写字号、颜色、间距和尺寸魔法值。

常规 UI 禁止直接散落：

- 字号；
- 行高；
- 间距；
- 控件高度；
- 固定宽度；
- 圆角；
- 颜色值；
- 图标尺寸；
- 点击热区；
- 阴影参数。

## 2. 三级 Token

### 2.1 基础 Token

负责原始数值：

- 字号；
- 行高；
- 间距；
- 控件高度；
- 宽度等级；
- 圆角；
- 图标尺寸；
- 点击热区；
- 基础颜色；
- 边框；
- 阴影；
- 动效时间。

### 2.2 语义 Token

负责表达用途：

- 主要文字；
- 次要文字；
- 禁用文字；
- 应用背景；
- 面板背景；
- 控件背景；
- 悬浮背景；
- 悬停；
- 选中；
- 焦点；
- 成功；
- 警告；
- 错误；
- 危险操作；
- 系统对象；
- 用户对象。

页面优先引用语义 Token，而不是直接引用基础颜色值。

### 2.3 组件 Token

只为重复使用、结构稳定的组件建立，例如：

- 图层行高度；
- 检查器标签列宽；
- 工具栏按钮内边距；
- 弹窗标题高度；
- 顶层页签高度；
- 日志行高。

禁止为单个页面、单个按钮或临时视觉问题创建专用 Token。

## 3. Token 修改权限

页面开发者只能引用 Token，不能擅自修改全局参数。

Token 修改必须：

1. 提交修改理由；
2. 说明影响范围；
3. 检查全部引用位置；
4. 完成全量 UI 回归验证；
5. 更新规范文档；
6. 经过规范变更审查。

不得为了修复一个页面，直接修改会影响整个项目的全局 Token。

## 4. 主题策略

当前只实现浅色主题，但 Token 架构必须支持未来换肤。

- 当前不开发和验收深色主题；
- 页面不得写死主题颜色；
- 未来主题通过替换语义 Token 映射实现；
- 不得为了新增主题重写页面结构。

# 四、颜色与视觉层级

## 1. 颜色原则

颜色体系采用：

> **功能与风格并重。**

基础界面使用浅色、低饱和蓝灰和青灰体系。

成功、警告、错误、危险等状态允许使用明确语义色，但应控制面积和饱和度，主要应用于：

- 图标；
- 边框；
- 状态条；
- 关键文字；
- 局部浅色背景。

禁止：

- 大面积高饱和色块；
- 荧光效果；
- 无明确含义的装饰颜色；
- 同一种颜色表达相互冲突的状态；
- 为追求风格而牺牲辨识度。

## 2. 对比度门禁

视觉可读性以人工真机验收为最终标准，自动对比度测试作为辅助门禁。

- 自动检查拦截明显不合格的文字和背景组合；
- 真机验收判断细线图标、禁用态、选中态和密集列表；
- 自动检查通过后，人工仍可判定不通过；
- 特殊视觉元素可以登记例外，但不能牺牲基本辨识度。

## 3. 四级背景体系

背景层级最多四级：

1. **应用底层背景**：编辑器窗口和应用基础背景；
2. **工作面板背景**：检查器、图层、工具栏等工作区域；
3. **控件内容背景**：输入框、信息块、列表内容区域；
4. **悬浮层背景**：弹窗、菜单、Tooltip、浮动工具条。

规则：

- 四级是上限；
- 各级主要通过轻微明度差建立结构；
- 页面不得自行增加第五级、第六级背景；
- 选中、悬停、警告、错误属于状态色，不属于结构背景层级。

## 4. 边框与阴影

- 普通区域主要依靠 `1 DIP` 浅色边框、分隔线和背景差异；
- 阴影仅用于真正悬浮的弹窗、菜单、Tooltip 和浮动工具条；
- 普通面板、按钮和列表项不得普遍使用阴影；
- 阴影参数必须统一；
- 阴影不得代替边框、焦点或选中反馈；
- 浅色主题阴影应轻、短、低透明度。

## 5. 圆角体系

建立三级圆角 Token：

- 小圆角：`3 DIP`
- 标准圆角：`6 DIP`
- 大圆角：`10 DIP`

使用约束：

- 编辑器主体主要使用 `3～6 DIP`；
- `10 DIP` 仅用于欢迎页、启动器、游戏 HUD 等大块视觉容器；
- 禁止大量胶囊形按钮；
- 禁止普通编辑器面板使用明显大圆角；
- 圆形控件只用于具有明确语义的对象。

# 五、文字体系

## 1. 字号单位

使用 Avalonia 的 DIP 逻辑尺寸。

普通编辑器界面采用固定字号等级，由系统和 Avalonia 负责 DPI 缩放，页面不得手工计算缩放倍率。

## 2. 响应式字号

采用：

> **固定字号等级为主，特殊场景有限响应。**

固定字号适用于：

- 菜单；
- 页签；
- 树形列表；
- 图层列表；
- 检查器；
- 日志；
- 表格；
- 普通按钮和输入框。

有限响应式字号可用于：

- 欢迎页；
- 启动器；
- 页面大标题；
- 游戏 HUD；
- 游戏主菜单；
- 大屏展示。

响应式字号必须设置统一的最小值和最大值。

## 3. 字体家族

采用分场景策略：

- 编辑器和开发工具优先使用系统中文 UI 字体和统一回退链；
- 正式游戏 UI 可以使用独立品牌字体；
- 正文、参数、数字、表格和日志必须优先保证可读性；
- 品牌字体缺字时必须自动回退；
- 字体资源和授权记录统一管理。

## 4. 字重体系

只允许使用规定字重集合：

- `Regular`：正文、字段值、说明、日志；
- `Medium / SemiBold`：页签、分组标题、选中项、重点按钮；
- `Bold`：页面主标题、关键结果、严重状态。

页面可以在允许的字重集合内选择，但不得引入新的字重等级。

`Light` 等字重默认禁止，品牌场景确有需要时申请例外。

## 5. 行高体系

每个字号定义标准行高，同时提供三个受控档位：

- 紧凑；
- 标准；
- 宽松。

场景建议：

- 紧凑：树、表格、日志、列表；
- 标准：检查器、表单、普通说明；
- 宽松：长文本、帮助文档、引导内容。

页面不得任意填写行高，也不得创建“半紧凑”等新档位。

# 六、间距与尺寸

## 1. 间距网格

采用：

> **4 DIP 主网格 + 少量半级。**

主要间距：

- `4 DIP`
- `8 DIP`
- `12 DIP`
- `16 DIP`
- `24 DIP`
- `32 DIP`

受控半级：

- `2 DIP`：细边框、插入线、微小视觉校正；
- `6 DIP`：紧凑控件内部间距。

其他数值原则上禁止随意使用。

## 2. 控件高度

统一三档：

- 紧凑：`24 DIP`
- 标准：`28 DIP`
- 强调：`32 DIP`

应用方式：

- 紧凑：工具栏小按钮、列表内操作、图标按钮；
- 标准：输入框、下拉框、普通按钮；
- 强调：弹窗主操作、欢迎页关键按钮。

页面不得自行创建 `26`、`30`、`34 DIP` 等高度。

## 3. 控件宽度

采用自适应为主、少量标准宽度等级。

- 按钮由文字、图标和标准内边距决定宽度；
- 输入框和下拉框跟随布局列宽；
- 检查器字段、数值输入和弹窗按钮可使用标准宽度 Token；
- 长文本使用省略、换行或 Tooltip；
- 禁止为了局部对齐填写大量不同宽度。

## 4. 内边距

统一三档基础内边距：

- 紧凑：`6×2 DIP`
- 标准：`8×4 DIP`
- 宽松：`12×6 DIP`

页签、菜单项和图标按钮等稳定组件允许建立组件级 Token。

## 5. 点击热区

按场景规定：

- 编辑器紧凑区域：最小 `24×24 DIP`
- 常规按钮和独立图标：最小 `28×28 DIP`
- 游戏与触控场景：最小 `36×36 DIP`

图标本体可以小于热区。

禁止通过缩小点击热区提高信息密度。

相邻热区必须避免重叠和误触。

# 七、信息密度与面板布局

## 1. 三档信息密度

- 紧凑：树形列表、日志、表格、工具栏、图层列表；
- 标准：检查器、设置页、普通弹窗、常规表单；
- 宽松：欢迎页、启动器、游戏主菜单、引导页面。

每个页面必须声明主密度。

允许组件按明确边界受控混用，但禁止同一列表或同一表单内无规律变化。

密度主要通过行高、间距和控件高度调节，不能仅靠缩小字号。

## 2. 面板边距

按密度规定：

- 紧凑：`8 DIP`
- 标准：`12 DIP`
- 宽松：`16 / 24 DIP`

树、表格、列表和日志等完整组件允许贴近面板边缘。

标题、工具区和正文必须保持统一对齐线。

贴边只作用于完整组件，组件内部内容不得无规则贴边。

## 3. 属性表单

采用响应式双模式：

- 面板宽度充足时：左标签、右字段；
- 面板较窄时：上标签、下字段。

要求：

- 使用统一切换阈值 Token；
- 同一属性组整体切换；
- 标签列宽和字段最小宽度统一；
- 切换后不能丢失单位、提示、错误信息和操作按钮。

## 4. 面板最小尺寸

不同面板类型建立统一最小尺寸 Token。

达到最小尺寸后，不得继续挤压文字和字段。

窗口继续缩小时，应按顺序：

1. 进入紧凑模式；
2. 折叠次要区域；
3. 隐藏低优先级面板。

折叠或隐藏后必须保留恢复入口。

初始非最大化窗口、最大化窗口和高 DPI 必须分别验收。

# 八、滚动与内容溢出

## 1. 普通面板滚动

默认采用：

> **固定标题和工具区，仅主内容区滚动。**

普通面板原则上只保留一个主滚动区。

底部关键状态可以固定。

## 2. 受控多滚动区

只有明确独立的组件允许拥有自己的滚动区域，例如：

- 顶层页签横向滚动；
- 独立大型列表；
- 独立预览区。

禁止无意产生内外嵌套滚动条和鼠标滚轮穿透。

---

# 九、顶层页签

## 1. 单行溢出

检查器、地图编辑器、偏好、模式、调试等同级页签必须保持单行，禁止换到第二行。

宽度不足时采用横向溢出：

- 鼠标位于页签栏时，滚轮控制横向滚动；
- 显示左右滚动箭头；
- 隐藏方向显示轻微渐隐；
- 当前页签自动滚动到完整可见；
- 首次发生溢出时显示一次性操作提示；
- 鼠标离开页签栏后，滚轮恢复控制内容区。

提示文字可采用：

> 滚动鼠标滚轮或点击箭头查看更多页签。

## 2. 全部页签入口

除横向滚动外，提供“全部页签”入口，允许直接跳转到任意页签。

不得擅自自动隐藏或重排用户页签。

## 3. 页签顺序

- 系统提供固定默认顺序；
- 普通模式下禁止直接拖动，避免误操作；
- 用户进入“管理页签”模式后可以调整；
- 自定义顺序保存到用户偏好；
- 不写入项目资产；
- 支持一键恢复默认顺序。

## 4. 页签关闭

- 核心页签不可关闭；
- 辅助页签允许关闭；
- 已关闭页签可从“全部页签”恢复；
- 至少始终保留一个可见页签；
- 关闭状态保存到用户偏好；
- 支持恢复默认页签。

## 5. 页签图标

- 核心页签使用“图标 + 文字”；
- 辅助页签默认使用文字；
- 空间不足时允许进入仅图标紧凑模式；
- 仅图标模式必须提供完整名称 Tooltip；
- 禁止使用 Emoji、Unicode 或系统字体符号作为正式图标。

# 十、图标体系

## 1. 基础方向

采用：

> **线性图标为主，状态图标允许填充、局部实心或受控双色。**

普通功能图标使用统一线性风格。

以下状态图标允许使用更强反馈：

- 选中；
- 锁定；
- 显示与隐藏；
- 成功；
- 警告；
- 错误；
- 开关状态；
- 危险操作。

状态表达可以采用：

- 局部填充；
- 实心状态点；
- 浅色辅助背景；
- 受控双色；
- 图标形态变化。

不能只依靠背景颜色表达状态。

## 2. 编辑器与工具图标

编辑器、调试工具、开发者控制台和启动器图标受本规范强约束：

- 统一笔画粗细；
- 统一视觉尺寸；
- 统一对齐方式；
- 统一颜色语义；
- 保证普通、悬停、选中、禁用状态可辨识；
- 禁止混用多个来源和风格的图标；
- 禁止 Emoji 和 Unicode 字符代替正式资产。

## 3. 正式游戏图标

《兵无常势》正式游戏图标属于本章的弱约束范围。

仍需遵守：

- 可辨识；
- 点击热区；
- 状态不能只靠颜色；
- 不出现缺字或错误资源；
- 相同功能保持基本一致；
- 满足对比度和可访问性底线。

允许独立决定：

- 图标美术风格；
- 填充、纹理和徽记；
- 军事符号表现；
- 游戏独立颜色体系；
- 品牌和世界观表达。

游戏图标的艺术表现自由，不得反向影响编辑器工具图标规范。

# 十一、状态、反馈与错误处理

采用分级反馈模式。

## 1. 普通成功

- 通过局部状态变化或底部短通知反馈；
- 不弹窗；
- 不打断连续工作流。

## 2. 重要成功

- 显示明确结果；
- 写入操作日志；
- 必要时提供下一步入口。

## 3. 警告

必须说明：

- 风险；
- 影响范围；
- 建议处理方式。

## 4. 错误

必须说明：

- 失败原因；
- 受影响对象；
- 当前状态；
- 恢复方式；
- 是否可以重试。

## 5. 危险操作

- 执行前确认；
- 明确对象、影响和不可逆后果；
- 危险按钮不得成为默认焦点；
- 不能只依靠红色表达危险。

## 6. 日志与通知优先级

- 错误和警告最高优先；
- 用户刚完成的操作次之；
- Render、Vulkan 等技术日志作为兜底；
- 技术日志完整保留，但不得覆盖用户操作通知；
- 拖动和连续交互过程不得刷屏写日志；
- 禁止所有操作都弹窗。

---

# 十二、输入、表单与校验

采用分阶段校验。

## 1. 输入过程中

只检查：

- 格式；
- 明显非法字符；
- 明显越界值；
- 无法继续输入的结构错误。

不得因用户尚未输入完整内容而频繁显示错误。

## 2. 失去焦点

执行完整字段校验：

- 数值范围；
- 字段格式；
- 必填条件；
- 单字段业务规则。

## 3. 提交时

执行：

- 字段间关系；
- 业务规则；
- 对象状态；
- 跨字段依赖；
- 最终完整性检查。

## 4. 错误呈现

- 错误显示在字段附近；
- 页面顶部提供问题汇总；
- 自动定位第一个错误；
- 用户输入内容不得因校验失败丢失；
- 不使用弹窗逐项提示普通字段错误；
- 错误状态不得只靠颜色。

---

# 十三、键盘、焦点与快捷键

## 1. 键盘可操作性

所有常用功能必须可以通过键盘完成。

## 2. 焦点顺序

- `Tab / Shift+Tab` 顺序符合视觉阅读顺序；
- 焦点不得跳入不可见、禁用或装饰性元素；
- 动态显示控件后，焦点顺序必须保持合理。

## 3. 焦点视觉

- 焦点态必须清晰；
- 焦点态不能与选中态混淆；
- 键盘焦点不能仅依靠颜色；
- 焦点边框不得被裁切。

## 4. 通用行为

- `Enter` 执行主要操作；
- `Esc` 取消、关闭或退出临时状态；
- 输入框编辑时屏蔽冲突的全局快捷键；
- 弹窗打开后，焦点限制在弹窗内部；
- 弹窗关闭后，焦点返回原操作位置。

## 5. 快捷键治理

- 快捷键集中登记；
- 模块不得自行抢占；
- 冲突必须在开发前解决；
- 菜单、Tooltip 和文档中的快捷键名称必须一致。

---

# 十四、拖拽、撤销与事务交互

采用完整事务式交互。

## 1. 标准流程

1. 操作开始时保存原状态；
2. 操作过程中只更新预览；
3. 松手或确认后一次性提交；
4. `Esc` 取消并恢复原状态。

## 2. 历史与 Dirty

- 一次拖拽只生成一个 Undo 历史节点；
- 无实际变化时不写历史；
- 无实际变化时不标记 Dirty；
- 失败操作不得污染历史。

## 3. 目标反馈

- 拖动热区统一；
- 插入线统一；
- 合法目标明确高亮；
- 非法目标明确拒绝；
- 必要时说明拒绝原因；
- 拖动过程不写逐帧日志。

---

# 十五、菜单、Tooltip 与上下文菜单

## 1. Tooltip

- 无文字图标按钮必须有 Tooltip；
- 文字已经足够明确的按钮可以不重复提示；
- Tooltip 说明“做什么”；
- 必要时显示快捷键；
- 禁止把长篇帮助文档塞入 Tooltip；
- 禁用控件应能说明不可用原因。

## 2. 上下文菜单

- 只放与当前对象直接相关的操作；
- 危险操作与普通操作分组；
- 菜单顺序统一；
- 图标尺寸统一；
- 快捷键显示方式统一；
- 禁止把无关全局功能塞入右键菜单。

## 3. 命名一致性

同一功能在以下位置必须使用相同名称：

- 顶部菜单；
- 右键菜单；
- 按钮；
- Tooltip；
- 快捷键登记；
- 日志；
- 帮助文档。

---

# 十六、弹窗与危险操作

采用分级确认体系。

## 1. 可撤销操作

原则上不弹窗，优先依靠 Undo。

## 2. 不可逆或高损失操作

必须确认，例如：

- 删除；
- 覆盖；
- 清空；
- 丢弃未保存内容；
- 破坏性导入；
- 重置不可恢复配置。

## 3. 确认弹窗

必须说明：

- 操作对象；
- 影响范围；
- 不可逆后果；
- 是否可以恢复；
- 取消方式。

## 4. 危险按钮

- 与普通按钮在位置和视觉上区分；
- 默认焦点不得落在危险按钮；
- 极高风险操作可要求输入对象名称二次确认。

## 5. 禁止事项

- 高风险操作不得提供“本次会话不再提示”；
- 禁止弹窗嵌套弹窗；
- 禁止普通成功操作弹窗；
- 禁止用弹窗代替字段级错误提示。

---

# 十七、空状态、加载与进度反馈

采用完整状态体系。

## 1. 空状态

必须区分：

- 初次进入；
- 当前无数据；
- 筛选无结果；
- 权限不足；
- 加载失败；
- 数据被删除或失效。

空状态应说明“为什么为空”。

有明确下一步时，只提供一个主要操作入口。

## 2. 短暂加载

短暂任务避免立即显示转圈，防止闪烁。

## 3. 可计算任务

显示真实进度：

- 百分比；
- 已完成量；
- 总量；
- 当前阶段。

禁止伪造进度。

## 4. 不可计算任务

- 显示不确定进度；
- 说明正在执行什么；
- 不显示虚假百分比。

## 5. 长任务

必须提供：

- 当前阶段；
- 已完成量；
- 取消入口；
- 失败原因；
- 重试或恢复方式。

取消后不得留下半完成数据。

后台任务不得无必要阻塞整个编辑器。

---

# 十八、高密度组件

树、列表、表格和日志建立统一基础体系。

## 1. 共用规范

统一：

- 基础行高；
- 字号；
- 图标尺寸；
- 对齐方式；
- 悬停态；
- 选中态；
- 焦点态；
- 禁用态。

## 2. 行内操作

- 默认收起；
- 悬停或选中时显示；
- 不得因显示操作按钮导致行内容跳动；
- 操作热区符合点击标准。

## 3. 表格

- 表头固定；
- 数据区滚动；
- 列宽支持受控调整；
- 支持恢复默认列宽；
- 排序、筛选和搜索状态清晰可见。

## 4. 长文本

- 默认省略；
- 提供 Tooltip、详情面板或展开查看；
- 不允许无限撑宽面板。

## 5. 大数据量

必须使用虚拟化，禁止一次性创建大量 UI 元素。

## 6. 日志

- 支持级别、来源、时间和分类筛选；
- 新日志不得强制抢走用户当前滚动位置；
- 用户处于底部时可以自动跟随；
- 用户离开底部后应暂停自动跟随；
- 批量操作必须显示作用对象和数量。

---

# 十九、高 DPI、分辨率与可访问性

## 1. DPI 验收

至少覆盖：

- 100%
- 125%
- 150%
- 200%

禁止使用物理像素手工补偿。

## 2. 分辨率与窗口

至少覆盖：

- 1080p；
- 2K；
- 4K；
- 初始非最大化窗口；
- 最大化窗口；
- 面板最小宽度；
- 高 DPI 下的窄窗口。

## 3. 文本与布局

文本放大后不得：

- 遮挡；
- 重叠；
- 截断关键内容；
- 破坏主要操作入口；
- 导致控件不可点击。

## 4. 状态表达

颜色不能作为唯一状态信息。

重要状态应结合：

- 图标；
- 文字；
- 形态；
- 边框；
- 位置。

## 5. 可识别名称

所有交互控件必须具备可识别名称。

## 6. 动画偏好

支持系统“减少动画”设置。

## 7. 屏幕阅读器

- 本轮必须建立基础结构；
- 高级支持可以分阶段完善；
- 未完成项必须登记明确待办；
- 不得无限期推迟。

---

# 二十、动效、响应速度与性能

采用轻量动效和明确性能门禁。

## 1. 动效用途

动效只用于解释状态变化，不用于装饰。

## 2. 推荐时长

- 悬停、选中：`80～120 ms`
- 展开、折叠：`120～160 ms`

## 3. 直接交互

以下操作必须直接跟手：

- 拖动；
- 缩放；
- 面板调整；
- 视口交互；
- 滚动；
- Gizmo 操作。

不得加入迟滞动画。

## 4. 性能要求

- 大列表滚动不得明显卡顿；
- 日志追加不得引发频繁 UI 重排；
- 后台渲染更新不得阻塞 UI；
- 动效不得阻塞输入、业务或渲染线程；
- 性能与动效冲突时，优先保证响应速度。

## 5. 禁止动效

禁止：

- 弹跳；
- 强发光；
- 长缓动；
- 大面积渐变动画；
- 装饰性循环动画；
- 影响操作判断的延迟动画。

---

# 二十一、正式游戏 UI 专项边界

正式游戏 UI 采用：

> **基础能力强约束，艺术表现弱约束。**

## 1. 强制遵守

游戏 UI 必须遵守：

- 点击热区；
- 键盘与焦点；
- 输入校验；
- 状态不能只靠颜色；
- 高 DPI 与分辨率适配；
- 错误、加载和进度反馈；
- 性能与响应速度；
- 危险操作；
- 可访问性底线；
- 数据完整性；
- 取消和恢复规则。

## 2. 弱约束范围

游戏 UI 可以独立决定：

- 美术风格；
- 品牌字体；
- 图标表现；
- 颜色主题；
- 面板造型；
- 动效风格；
- 信息布局；
- 军事符号；
- 世界观表达。

## 3. 边界

游戏专项规则不得降低基础可用性门禁。

游戏艺术表现不得反向污染编辑器工具规范。

# 二十二、规范执行、验收与变更

采用完整执行闭环。

## 1. Token 落地

规范中的稳定数值必须转为 Token。

## 2. 自动化门禁

可自动判断的规则必须建立：

- 单元测试；
- 源码合同测试；
- 静态检查；
- 检查脚本；
- 结构审计；
- Token 引用检查。

## 3. 真机验收

视觉、交互和真实显示效果必须进行真机验收。

自动测试通过不能替代真机验收。

## 4. UI 开发轮报告

每个 UI 开发轮必须附带：

- 规范符合性清单；
- 自动化验证结果；
- 真机验收清单；
- 例外登记；
- 已知问题；
- Git 状态；
- 版本状态；
- Warning / Error 状态。

## 5. 违规处理

发现违规时：

- 不得口头放行；
- 不得标记为“与本轮无关”；
- 不得推迟到未知未来；
- 必须修复或正式登记受控例外。

## 6. 规范与 Token 变更

变更必须：

1. 说明原因；
2. 说明受影响组件；
3. 更新文档；
4. 更新 Token；
5. 更新测试；
6. 执行全量 UI 回归；
7. 完成真机复验；
8. 保留变更记录。

## 7. 完成条件

同时满足以下条件后，才能宣布 UI 规范实施阶段完成：

- 自动测试通过；
- 真机验收通过；
- 全解决方案 `0 Warning / 0 Error`；
- 旧 UI 整改清零；
- 例外全部登记；
- 文档、Token、测试一致；
- Git 工作区干净；
- 提交与远端一致；
- 版本和变更记录完整。
