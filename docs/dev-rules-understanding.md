# 玄域引擎 · 开发规范「为什么这样规定」（理解手册）

> 本文件是 `dev-rules.md` 的**解释层**：讲事故来源、设计动机、历史坑。
> 它用于判断接手者是否真正读懂了规范，**不可当作可灵活发挥的执行手册**。
> 执行只看 `dev-rules.md`。

---

## 总精神

这套规范不是"代码优雅主义"，而是 **事故驱动 + 防御性 + 小步封版**。

它不信任临场判断，而是把"曾经翻车"用 **代码宪法 + 自动化门禁 + 审计 / 封版文档** 三层焊死。核心要防的几类反复出现的问题：

- 大文件失控、职责混杂
- AI 越界开发（一次铺太大）
- 高频日志 / 诊断拖垮 UI
- Vulkan 生命周期与 UI / 窗口 / Surface / Swapchain / Dispose 顺序混绑
- UI 与渲染互相污染
- 文档 / 文件树不同步

---

## 1. 5+100 形态门禁 — 为什么

**事故来源**：大文件失控 → 只读 diff 无法审计；多职责混装 → 改动牵一发动全身、回归难定位。

**设计动机**：文件小 = 评审面小 = 事故面小。`CodeFileBudgetTests` 门禁才得以可行（锁行数、白名单、`GlobalUsings ≤ 100`）。

**常见误读（必须避免）**：
- 误读："`≤100 行，复杂文件 ≤150 行，>200 禁止`" → 新 agent 会理解成"普通 100、复杂 150 也行"。
- 正解：**单文件 ≤100 行是硬门禁**；>100 只能作为历史债务或明确审计过的临时例外；**禁止把"复杂"作为自然突破 100 行的理由**。超过 100 行必须先说明原因、列入债务或立即拆分。
- 目录规模（<7 文件）只是建议 / 预警，优先级低于单职责与 100 行硬门禁。切勿为凑目录数量把职责塞回大文件。

## 2. 依赖方向硬隔离 — 为什么

**事故来源**：UI 生命周期、窗口句柄、Surface、Swapchain、Dispose 顺序混在一起 → 卡死、Swapchain 销毁顺序混乱、访问违例（最近分支 `fix/RZ-Fix1-editor-access-violation`）。

**设计动机**：依赖方向图就是防"回潮"的墙。RZ 系列审计反复强调"目标依赖方向 vs 当前残留"。`Core` 在最底层、`Vulkan` 只在 `Render.Vulkan`、`Avalonia` 只在编辑器，三者互不反向渗透。

**精确表述（避免含糊）**：
- 不是笼统说"Editor.UI 不碰 Vulkan"，而是：**Editor.UI 不得直接引用 `Silk.NET.Vulkan`、不得持有 Vulkan 对象、不得直接控制 Vulkan 生命周期**。
- 但 UI 可以通过 `Render.Abstractions` 调用抽象能力、通过薄 `Route` 发起诊断、显示后端探针结果、记录低频生命周期日志——这些是允许的。
- **过渡期现实**：当前 `XuanYu.Editor.UI` 已含 `VulkanProbeRoute.cs` / `ViewportNativeHostRoute.cs`，属 VK1 最小探针的暂时接受；目标是在 VK2 / VK3 前改为 `Editor.UI → Abstractions`、`Editor.Win → Vulkan`、`Render.Vulkan → Abstractions`，让平台组合根负责装配 Vulkan 后端，而非 UI 项目直接认识实现。

## 3. 高频链路纪律 — 为什么

**事故来源**：9.0D 真实事故——拖动 / 高频输入路径里直接写 `WorldState`、刷 Inspector / Diagnostics、写普通日志、提交 Undo、重建资源 → UI 线程卡死、全窗口失去响应。

**设计动机**：把"交互高频"与"状态提交"在时间上彻底切开。一条原则保护三件事：**UI 不卡 + 撤销历史不被污染 + 日志不爆**。`gizmo_drag_audit` 的验证结论就是：拖动过程 `UI=是 / WorldState=是 / Diagnostics=是` 全为 0。

**这是共同规则**：输入、Gizmo、Viewport、Vulkan Resize 都适用——高频路径只 Preview，松手才 Commit，Esc 取消。

## 4. 日志边界 — 为什么

**事故来源**：诊断回调直接绑 UI 日志 → 高频事件逐条进日志 → 卡顿；以及"折叠 / 节流 / Buffer"被误当成源头治理，结果仍出现如 `【NativeHost】尺寸变化 重复 138 次` 这类爆量。

**设计动机**：测量不能影响被测对象。节流只是低频日志 UI 刷新的保护层，**不是**允许高频事件进入 `EditorLogBus` 的理由。

**正确原则**：高频事件**先在源头合并**；日志总线**只接收低频事实**。折叠 / 节流 / Buffer 不能替代源头合并。

## 5. Vulkan 阶段边界 — 为什么

**事故来源**：一次性把 Surface / Swapchain / CommandBuffer / 渲染循环全做，生命周期交织、Dispose 顺序混乱、难以审计。

**设计动机**：阶段边界比技术规则更硬。每一阶段只做一件事，且明确"不做什么"，防止回潮夹带。

**阶段边界（硬）**：
- VK1：只探针，不 Surface。
- VK2：只 NativeHost / HWND 生命周期，不 Surface。
- VK3：只 Surface 生命周期，不 Swapchain 扩张。
- VK4：Swapchain 最小闭环。
- 防：VK2 夹带 Surface / VK3 夹带 Swapchain / VK4 夹带真实渲染循环。

## 6. 中文化铁律 — 为什么

**设计动机**：中文给"人"（开发者 + 用户）看；英文给"机器"看（搜索、测试断言、跨语言扩展、日志筛选）。是"品牌面向中文开发者 + 代码要可检索 / 可国际化"的折中。例：`Core.InvalidArgument`（码·英文）/ `参数无效。`（信息·中文）。

## 7. 范围与结构纪律 — 为什么

**事故来源**：范围漂移。`ShellV2` 从"最小骨架"滑向"重做整套编辑器"被叫停（冻结：不回滚、不继续、不扩大）。

**设计动机**：每个阶段末尾带"禁止项确认"清单，把"我这次没越界"变成可勾选的审计项。结构性变更必须同步 `file-tree.md`，否则后人无法对照真实结构。

## 8. 命名与品牌 — 为什么

**设计动机**：品牌迁移是"用户可见层先换，代码层逐步清"，用门禁 + 终验保证不回潮。`FluidWarfare` 仅作历史代号，不作正式品牌名；命名空间目标 `XuanYu.Engine.*`。

## 9. 构建 / 测试 / 审计门禁 — 为什么

**设计动机**：你写的不是代码，是"可被后人 audit 的历史"。每份 audit 都是给未来自己的防坑说明书。`dotnet build 0 warning/0 error` + `CodeFileBudgetTests` 是物理门禁；审计 → 修复 → 封版验证是流程门禁；冻结 / stash 纪律防止半成品污染主线。

## 给新 agent 的"常见误读"速查

1. ❌ 复杂文件可 150 行 → ✅ 单文件 ≤100 行是硬门禁，>100 须有原因 / 债务 / 拆分。
2. ❌ Editor.UI 不碰 Vulkan（含糊）→ ✅ 不得直接引用 / 持有 Vulkan 对象 / 控制生命周期；可经 Abstractions / Route / 显示探针。
3. ❌ 目录 <7 文件与 100 行同级 → ✅ 目录规模只是预警，优先级低于单职责与 100 行。
4. ❌ 节流允许高频事件进日志 → ✅ 节流是低频 UI 保护层，高频须在源头合并，总线只收低频事实。
5. ❌ Vulkan 生命周期一次性做完 → ✅ VK1–VK4 阶段边界比技术规则更硬，禁止跨阶段夹带。
